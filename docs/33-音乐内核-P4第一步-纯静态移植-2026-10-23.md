## 一、为什么先挑音乐

文档 13 的 P4 是「音乐全链」，原本排在最后（因为最大）。
但没有真机时，它反而成了**唯一能真正推进**的一块 —— 原因是它由三段组成，
只有最后一段（播放器）碰 UI：

| 段 | 依赖 | 没真机能做到什么 |
|---|---|---|
| ① 加密（eapi/weapi/linuxapi） | 纯算法 | **100% 确定性正确** |
| ② 解析（LRC / 变量替换） | 纯算法 | **100% 确定性正确** |
| ③ 网络（NSURLSession） | 设备 | 代码写完，等真机 |
| ④ 播放器 / 卡片 | 设备 | 没动 |

所以这一轮只做 ①②，并顺手把 ③ 的骨架按 Java 版逐字段抄好。

## 二、做了什么

### 2.1 `FDMMusicCrypto.c/h` —— 加密层（纯 C11，零依赖）

自带 AES-128（FIPS-197）、MD5（RFC 1321）、Base64、hex；
RSA 因为要 1024-bit 模幂，抽成回调 `fdm_rsa_raw_fn`：

- **iOS**：`Security.framework`（`FDMMusicCryptoIOS.m`）
- **Linux 测试**：OpenSSL（`RSA_public_encrypt(RSA_NO_PADDING)`）

三个通道与 `GmMusicCrypto.java` 逐行对应：

```
eapi     = hexUpper(AES-128-ECB("e82ckenh8dichen8", uri + sep + json + sep + md5(...)))
linuxapi = hexUpper(AES-128-ECB("rFgB&h#%2?^eDg:Q", json))
weapi    = params(Base64(AES-128-CBC(secretKey, Base64(AES-128-CBC(presetKey, json)))))
           + encSecKey(hex(RSA_RAW(reverse(secretKey))))
```

### 2.2 `FDMMusicApi.h/m` —— API 客户端

`search` / `songUrl` / `songDetail` / `lyric` / `postWeapi` 全部照抄 Java 版的
路径、参数名、cookie 字段顺序、UA 档位（pc / android / iPhone 三档成对）。

**唯一的结构差异：异步。** Java 用 `HttpURLConnection` 阻塞跑，
iOS 绝不能阻塞主线程 ⇒ 全部 completion 回调，固定投递回主线程。

细节全部照抄，包括那些"看不出为什么"的：

| 细节 | 为什么照抄 |
|---|---|
| `versioncode=140`、`resolution=1920x1080` | 服务端会看 |
| `mobilename=`、`__csrf=` 留空 | 真客户端也空着 |
| `buildver` = 秒级时间戳前 10 位 | 照抄 |
| `requestId` = `ms_4位序号` | 照抄 |
| 搜索后补一次 `songDetail` 拿封面 | 搜索接口只给 `picId`，不给 `picUrl` |
| 用 ephemeral session + 手动 Cookie | 避免被 shared 池污染、也避免自动重定向吞掉 `Set-Cookie` |

### 2.3 `FDMPromptVars.c/h` —— 系统提示词变量引擎

`{music}` `{music_or_none}` `{song}` `{artist}` `{album}` `{music_pos/dur/left}`
`{music_state}` `{lyric}` `{lyric_prev}` `{lyric_next}`，加上 `[[ … ]]` 糖。

### 2.4 `FDMLyric.c/h` —— LRC 解析

`[mm:ss]` / `[mm:ss.xxx]` / `[mm:ss:xxx]`，一行多标签取最后一个，
元数据标签自动忽略，按时间稳定排序，`around(pos)` 给三句。

## 三、⭐ 怎么在没有真机的情况下证明"代码是对的"

这是这一轮真正的收获。

### 3.1 三层证据，缺一不可

| 层 | 手段 | 能证明什么 |
|---|---|---|
| **标准向量** | FIPS-197 AES / RFC 1321 MD5 | 原语本身没写错（不是"能跑"就行） |
| **对拍** | 真跑 `GmMusicCrypto.java` 打印向量，C 版逐字节比 | **与已验证的安卓实现完全一致** |

只有标准向量 ⇒ 不知道网易的报文组装对不对；
只有对拍 ⇒ 不知道 Java 版本身有没有错；
只有真请求 ⇒ 可能只是碰巧。

## 四、真机自检：把"等真机"变成"看一眼日志"

`FDMProbe.m` 的 6s 定时器里加了一段（不联网也能跑）：

```objc
FDMMusicCryptoInstall();          // MD5/AES/Base64 + RSA 固定向量
FDMPromptVarsInstall();           // 20 条变量规则断言
FDMLyricInstall();                // 15 组 LRC 断言
FDMMusicNetworkProbeIfEnabled();  // 开关 music_probe 打开时打一次真搜索
```

设备上应该看到：

```
[music] crypto ✓（MD5/AES/Base64/RSA 全部与 Java 版一致）
[pvar] 变量引擎 ✓（20 条用例：空值/双开方括号/歌词闸门/未知花括号）
[lyric] LRC 引擎 ✓（15 组断言：多标签/小数位/前奏/元数据忽略）
```

**这三行不出现，就说明 iOS 侧编译/链接/签名出了问题，跟算法无关。**
想看网络：

```bash
echo 1 > Documents/fdm-music-probe.txt     # 下次启动自动打一次搜索
```

**开关**（在 `Documents/fdm-debug.json` 里加键，**不要覆盖已有键**）：

```json
{ "pvar_on": true, "pvar_lyric": false, "music_probe": true }
```

| 键 | 作用 | 默认 |
|---|---|---|
| `pvar_on` | 音乐变量总开关（关着 ⇒ 连 `[[ ]]` 都不碰） | `false` |
| `pvar_lyric` | 歌词变量开关（⚠️ 版权：开了歌词会随提示词上传） | `false` |
| `music_probe` | 启动时打一次真实搜索（只用于排查） | `false` |

> 改完不用重启：`pvar_*` 有 5 秒内存缓存，`music_probe` 下次启动生效。

## 五、⚠️ 三个坑（都是这一轮才发现的）

### 5.1 `SecKeyCreateEncryptedData` 的 `kSecPaddingNone` 在 iOS 15 已废弃

`kSecPaddingNone` 是个 `SecPadding` 枚举值（`0`），传给要求
`SecKeyAlgorithm` 的参数 ⇒ 编译器直接报
`expression which evaluates to zero treated as a null pointer constant`。

正确写法是**算法串**：

```objc
SecKeyCreateEncryptedData(key, kSecKeyAlgorithmRSAEncryptionRaw, data, &err);
```

并且 `RSAEncryptionRaw` 要求输入**正好等于模长**（1024-bit = 128 字节），
所以 16 字节 secretKey 必须先**左补 0 到 128 字节**（左补 0 不改变大端整数值，
等价于 node-forge 的 `'NONE'` 模式）。

> 这一条已经写进自检：真机上如果 RSA 向量不过，日志会直接把 got/want 打出来。

### 5.2 Java 版 `GmPromptVars` 的注释和实现对不上

类注释写：

> 「块内必须至少有一个变量 —— `[[普通方括号内容]]` 会被原样保留（**脱壳都不脱**），避免误伤正常文本」

但实现是：

```java
if (!(hasVar && allEmpty)) out.append(inner);   // 无变量时也 append(inner) ⇒ 脱壳
```

也就是说**注释承诺不脱壳，代码实际会脱壳**。
`[[普通方括号]]` 在安卓上会变成 `普通方括号` —— 悄悄吃掉两个字符。

iOS 版按**注释的意图**实现（无变量 ⇒ 连壳原样保留），
因为"不误伤用户正常文本"比"跟有 bug 的实现保持一致"重要。
用例 #7 专门钉住这个行为。

> 安卓那边要不要一起改，等主人拍板。

### 5.3 ★ ATS：宿主 plist 关掉了 http，而网易云的播放地址是 http

这个坑**只有在静态看一遍 Info.plist 才会提前发现**，否则真机上就是
「搜索正常、歌词正常、一点播放就永远转圈」，而且不报错。

```
app/Payload/DeepSeek Chat.app/Info.plist
  NSAppTransportSecurity = { NSAllowsArbitraryLoads = false }
```

而 `songUrl` 返回的是：

```
http://m801.music.126.net/2026.../xxx.mp3?vuutv=...
```

⇒ `AVPlayer` / `UIImage` 都会被 ATS 直接拒绝。

**验证过的解法**（2026-10-23，同一 URL 同一路径）：

| 协议 | 结果 |
|---|---|
| `http://m801…mp3` | `206` `audio/mpeg` 1024 B |
| `https://m801…mp3` | `206` `audio/mpeg` 1024 B ✅ |

⇒ 直接在客户端把 `http://` 换成 `https://`，**不改宿主 plist**
（改 plist 会破坏签名，TrollFools 注入的包也白搭）。

代码里落成 `FDMPreferHTTPS()`：`songUrl` 与 `picUrl` 都过一遍。
（封面那边实测本来就返回 `https://p1.music.126.net/...`，只是兜底。）

> 顺带记两条将来做播放器时要处理的：
> 1. `AVAudioSession` 要设 `AVAudioSessionCategoryPlayback`，否则**静音键一拨就没声**；
> 2. 网易云的播放 URL 带时间戳签名，**约 20 分钟过期** ⇒ 播放前取一次，别缓存太久；
> 3. 宿主 `UIBackgroundModes` 里大概率没有 `audio` ⇒ 切后台会被挂起，别承诺"后台播放"。
