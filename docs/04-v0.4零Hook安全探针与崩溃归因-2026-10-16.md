# 04 · v0.4 零 Hook 安全探针 & 崩溃归因实验

> 2026-10-16 · 尼得亚伯 🐲
> 背景：v0.2 崩（Hook 太重，已定位）→ v0.3 修了所有已知雷 → **主人反馈：还是崩**

---

## 〇、结论先行

**v0.3 还崩，说明"探针太重"可能不是主因。** 现在必须用实验把两个假设分开：

| 假设 | 表现 |
|---|---|
| **A. 探针太重**（Hook / IO 拖慢） | 换 v0.4（零 Hook）→ **不崩** |
| **B. 反作弊检测注入**（数美 / 完整性校验） | 换 v0.4（零 Hook）→ **照样崩** |

v0.4 就是为这个实验设计的。

---

## 一、v0.4 设计：极端保守

| 原则 | 做法 |
|---|---|
| **零 Hook** | 一行 `method_setImplementation` / `class_replaceMethod` 都不做（已 grep 验证：0 处） |
| **只调公开 API** | 像普通 App 一样：`[MMKV defaultMMKV]` → `allKeys` / `objectForKey:` |
| **阶段标记** | 7 个任务分时执行，**每个任务开始/结束都写标记** |
| **心跳** | 每 5 秒一条，记录"活了多少秒" |
| **全部后台队列** | `QOS_CLASS_UTILITY`，不占主线程 |

### 任务时间表

```
STAGE 0   立即    构造函数进入（排程日志）
+8s       S1      镜像列表              → fdm2-images.txt
+15s      S2      KV dump #1（启动期）  → fdm2-kv.txt
+25s      S3      blob                 → fdm2-blob.bin / .json / .txt
+40s      S4      类结构 dump          → fdm2-classes.txt
+70s      S5      KV dump #2（登录后）  → fdm2-kv.txt（覆盖）
+75s      S6      blob #2
+100s     S7      收尾
```

### 产出（App 沙盒 `Documents/`）

```
fdm2.log          阶段标记 + 心跳（★ 最关键，判断崩在哪一步）
fdm2-kv.txt       mmkv.default 全量键值
fdm2-blob.bin     原始 blob
fdm2-blob.json    blob 的 JSON 美化版（如果是 JSON）
fdm2-classes.txt  相关类结构
fdm2-images.txt   已加载镜像（能看出有没有 ellekit/frida 等注入痕迹）
```

## 二、判读表（拿到日志后照着看）

| `fdm2.log` 的样子 | 含义 | 下一步 |
|---|---|---|
| **连 STAGE 0 都没有** | 构造函数没跑 → **dylib 没被加载** | 查 TrollFools 注入列表 |
| 有 STAGE 0，但心跳在某个 STAGE 中断 | **崩在那一步** | 精准定位 |
| 心跳到 S2 后断 | KV dump 触发了问题 | 改用逐键读取 |
| 全部 STAGE + S7 完成，App 没崩 | ✅ **反作弊不管注入，是 v0.2/0.3 太重** | 回 v0.3 但进一步减重 |
| 心跳正常但 App 在**登录后**崩 | **数美在登录时检测** | 需要绕过反作弊 |
| STAGE 全过 + 心跳到 100s+ 都很平稳 | ✅ 完全安全 | 用 v0.4 拿数据，业务另设计 |

> ⭐ `fdm2-images.txt` 特别有价值：如果里面出现 `ellekit` / `Substrate` / `frida`，
> 说明**越狱注入框架也在往 App 里塞东西** —— 那才是反作弊真正会抓的把柄。

## 三、主人的"先登录再注入"策略 —— 其实是个好实验

**先登录、再注入**，等价于**把"登录流程"从实验里摘出去**：

| 情况 | 推论 |
|---|---|
| 登录后注入 → **不崩** | 崩溃与**登录流程**强相关（登录时的 MMKV 风暴 or 登录时的风控检测） |
| 登录后注入 → **还崩** | 与登录无关，是**注入本身**或**某个常规 API 调用**有问题 |

⚠️ 注意：TrollFools 是**改 App bundle**，注入后必须**重启 App**才生效 —— 所以"先登录再注入"能不能成立，取决于主人用的注入器是否支持"运行时热注入"。如果只能重启注入，那就**恢复登录态后重启**（Keychain/MMKV 里的登录凭证还在，App 起来就是已登录状态）—— 效果等价。

## 五、为什么 v0.3 还可能崩 —— 剩下的可疑点

| # | 可疑点 | 说明 |
|---|---|---|
| 1 | **`NSLog` 本身** | 在 Hook 里调 NSLog，若宿主也持有 OSLog 相关锁，可能死锁 |
| 2 | **`SafeStr` 调 `isKindOfClass:`** | 是宿主方法；虽轻，但在 MMKV 锁内调用宿主代码仍有风险 |
| 3 | **`DumpKV` 触发大量 `objectForKey:`** | 若某键的值极大/嵌套，`SS()` 展开可能爆内存 |
| 4 | **数美反作弊** | `SmCaptcha.framework` + `fengkongcloud.com`；登录时最活跃 |
| 5 | **越狱注入框架痕迹** | Dopamine 的 ElleKit 若也注入本 App，反作弊一抓一个准 |

> v0.4 一次性把 1/2/3 全部排除（零 Hook、无 NSLog-in-hook），只剩 4/5 需要靠 `fdm2-images.txt` 和心跳判断。

## 六、附带建议：检查 ElleKit 是否也注入了 DeepSeek

Dopamine 默认会用 ElleKit **全局注入所有 App**。如果 DeepSeek 也在名单里：
- App 的 `_dyld_image_count()` 能直接看见 `libellekit.dylib` / `Substrate` → **反作弊的铁证**
- **建议：在 Dopamine 设置里把 DeepSeek 排除掉**（我们走 TrollFools，根本不需要 ElleKit）

这条比"新建挂载"有用得多 —— 而且**零成本**。
