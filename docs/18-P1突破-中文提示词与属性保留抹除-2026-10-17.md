## 二、文档 14 的结论被推翻了：抹除其实一直是好的

文档 14 说「显示层 0 命中、全军覆没」。**这个结论是错的**，
原因是当时只测了 `tag`（零宽）模式 —— 零宽字符本来就不显示，
所以抹除 hook 没机会命中，看起来像「没工作」。

改用 `fdm` 明文定界后，抹除立刻生效。

> **教训**：用「看不见的效果」去验证「隐形机制」，等于没验证。
> **换一个可观测的模式再测一次**，是最便宜的证伪手段。

## 三、⭐ 关键 bug：抹除后「字小一半 + 变黑」

### 现象（主人实拍）

`⟦FDM⟧` 抹掉后，那条用户消息的气泡里：
- 字比旁边**小一半**
- 颜色**变成黑色**
- 气泡框也小

### 根因

```objc
// FDMStrip.m · st_setAttributedText（旧代码）
NSString *cs = FDMStripMarks(str);
if (cs != str) {
    clean = [[NSAttributedString alloc] initWithString:cs];   // ★★★
}
```

`initWithString:` 会**新建**一个纯字符串富文本 ——
宿主设置的 `attributes`（字体字号、前景色、段落样式、字距）
**统统丢失** ⇒ 渲染成系统默认 ~12pt 黑字。

### 修法：就地删除，保留属性

```objc
NSMutableAttributedString *m = [as mutableCopy];
int guard = 0;
while (m.length > 0 && guard++ < 32) {
    NSRange a = [m.string rangeOfString:kOpen];
    if (a.location == NSNotFound) break;
    NSRange tail = NSMakeRange(a.location, m.length - a.location);
    NSRange b = [m.string rangeOfString:kClose options:0 range:tail];
    NSUInteger end = (b.location == NSNotFound) ? m.length : NSMaxRange(b);
    if (end < m.length && [m.string characterAtIndex:end] == '\n') end++;
    if (end <= a.location) break;
    [m replaceCharactersInRange:NSMakeRange(a.location, end - a.location)
                     withString:@""];
}
// 与 FDMStripMarks 对齐：吃掉开头多余换行（同样保属性）
while (m.length > 0 && [m.string characterAtIndex:0] == '\n')
    [m replaceCharactersInRange:NSMakeRange(0, 1) withString:@""];
```

`replaceCharactersInRange:withString:@""` 只改动被删区间，
**其余文字的 attributes 一动不动** ⇒ 字号/颜色/行高全部保持。

> **通用教训**：凡是「过滤/清洗富文本」的操作，
> **永远不要用 `initWithString:` 重建**。
> 一定要 `mutableCopy` + 区间删除/替换。

## 四、新发现：`tag` 零宽模式在 iOS 不可用

主人 17:17 第二张截图：

```
?????????你好     ← 零宽字符渲染成一排豆腐块
```

**原因**：iOS 系统字体（PingFang SC 等）**没有** U+E0000–E007F
（Tag 区）的字形，UIKit 直接画成「缺字形」方块。

**处置**：
- 默认模式从 `tag` 改成 `fdm`
- 设置页说明改成「⚠️ 不推荐：iOS 字体没有字形，会渲染成一排 ? 豆腐块」

| 模式 | 中文 | 隐形 | iOS 可用性 |
|---|---|---|---|
| `fdm`（⟦FDM⟧ 定界 + 渲染抹除） | ✅ | ✅（抹除后） | ✅ **推荐** |
| `tag`（零宽 Tag 区） | ❌ 只能 ASCII | ✅（本来就没有字形） | ❌ **豆腐块** |
| `plain`（明文前缀） | ✅ | ❌ 看得见 | 仅对照实验 |

## 五、配置系统的一个坑（排查时会误导）

`fdm-debug.json` 的 `log_level` 会被 **App 回写**成默认值 `W`：

```
我写进去：  "log_level" : "D"
App 读完后： "log_level" : "W"    ← 被 FDMConfig 回写覆盖
```

后果：`FLOGI` / `FLOGD` 全部被过滤，看起来像「功能没跑」
（实际上功能是跑的，只是日志不落地）。

**绕过方法**：
1. 通过 🦖 设置界面改（走 FDMConfig 正常的 setValue 路径）
2. 或在 App **没运行**时写文件，且 App 启动后不要再触发回写

**建议下次改进**：`log_level` 不该被回写 ——
它是调试开关，不是用户配置。可以给它加一个「不持久化」标记。
