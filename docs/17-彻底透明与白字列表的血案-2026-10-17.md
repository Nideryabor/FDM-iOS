# 17 · 「彻底透明」与白字列表的血案 · 2026-10-17

> 尼得亚伯 🐲 · 宿主 DeepSeek Chat 2.6.2 / iPhone 7P / iOS 15.8.4

---

## 一、一句话结论

**`bg_clear_all`（彻底透明）是「白字列表页」的毒药。**
它在聊天页让气泡融进背景（好看），但在**会话抽屉 / 设置页**这类
「白字压在照片上」的页面，会把容器底色清光 ⇒ 白字直接画在亮背景上
⇒ 亮处整片「看不见」⇒ 看起来像「下面的列表项消失了」。

**这不是渲染 bug，是被背景吃掉了。**

## 三、踩爆的坑（代价最大）

### 3.1 把「给抽屉加实底」当成解决方案 ⇒ 设置页变成完全不透明

```
panelBox.backgroundColor = #1C1C1E / 0.94
```

**为什么错**：`BTApplyPanelScrim` 找「面板容器」时按
"宽度 <= host 宽度"挑，第一个命中是 **UIImageView**（我们自己的背景图）；
改成"找最大滚动视图的 superview"后，又挑到
`SessionListSearchResultsView`（搜索结果的列表）——
一个只在搜过东西后才存在的视图。

**教训**：**不要用几何/启发式去猜"哪个视图是面板"**。
宿主 UI 结构每一版都可能变，猜法一定翻车。

### 3.2 忽略了一件根本的事：清理是**全局**的

诊断日志当时是这样的：

```
clear_all 处理 MessageViewController（聊天页=1）    ← 以为只清了它
clear_all 处理 SessionListViewController（聊天页=0）← 以为没清
```

但抽屉照样被清。因为真正清底色的**不是** `BTStripEverything`，而是：

| hook | 挂在哪 | 影响范围 |
|---|---|---|
| `bt_scrollLayout` | `UITableView` / `UICollectionView` **本类** | 全 App 所有表格 |
| `bt_cellLayout` | 所有 `DeepSeek*Cell` 类 | 全 App 所有 cell |

它们只看"开关开没开"，不看"这个视图属于哪个页面"。

**修法**：加 `BTViewBelongsToChat(v)` —— 沿 superview 链找 `nextResponder`
里的 VC，只有 `MessageViewController` 才动手。

### 3.3 二次伤害：`BTApplyScrollBG` / `BTClearContainerBG` 也是无条件的

即使在 `BTApplyBackground` 里给 `BTStripEverything` 加了聊天页白名单，
后面还有两个**无条件**调用会把非聊天页的面板容器清掉、并在滚动视图
祖先上贴图。

**最终分叉**：

```objc
vc.view.backgroundColor = [UIColor clearColor];

if (BTVcIsChatPage(vc)) {
    BTClearContainerBG(vc.view);
    BTApplyScrollBG(vc.view, img, nil, 0);
} else {
    /* 非聊天页：只贴图，一个字节都不改 */
}
```

## 五、气泡透明：下次怎么做才对

**核心矛盾**：`bg_clear_all` 想要的效果（气泡跟背景融合）和
"列表可读"（需要实底）在同一套清理逻辑里没法共存。

**下一版必须走「按视图类型精确清理」，不要整棵树遍历**：

```
只清这几类（聊天页内）：
  • MessageCell / UserMessageCell / AgentMessageCell 的 contentView
  • RequestFragmentView / ResponseFragmentView
  • UserRequestBubbleView / UserBubbleView
  • 消息区的 UIVisualEffectView（灰蒙蒙的来源）

绝不碰：
  • UIScrollView 的祖先（那是面板底）
  • UIListContentView（那是 cell 内容边界）
  • 任何 superview 链上能找到 SessionList/Profile VC 的视图
```

**验证方法（这次学到的）**：
1. 先只开 `bg_clear_all`，不要同时开 `bg_fix_modal` —— 变量要一次只动一个
2. 每一步都要**真机看抽屉 + 设置页**，不能只看聊天页
3. 用 `[cell]` / `[panel]` 探针在日志里确认「清了几个、清了谁」

## 六、方法论补充

### 「改了没效果」时的三层排查

```
① 日志确认代码跑了没有（FLOGW 打点）
② 跑了但没效果 → 是不是**别的地方**又改回去了？
   这次就是：BTStripIfChatPage 生效了，但 bt_scrollLayout 还在全局清
③ 跑了、也只有一个地方改 → 是不是**动画期间**被冲掉？
   （present 探测器就是为这个加的）
```

### 「多个 hook 改同一个属性」极其危险

今天 `backgroundColor` 被 5 处代码碰过：

```
bt_cellLayout / bt_scrollLayout / BTStripEverything
BTStripSubtreeBG / BTStripBubbles / BTApplyScrollBG
```

**建议**：以后所有改 `backgroundColor` 的地方统一走一个函数，
带 `(view, 允许的页面类型)` 两个参数，否则永远在互相打架。

### 诊断 hook 的性能陷阱

为了抓"谁把 cell 藏起来"，hook 了 `UIView.setHidden:` 并打
`[NSThread callStackSymbols]`。结果：**长按卡顿**（每次 setHidden 都取栈）。

**教训**：诊断 hook 必须满足三条
1. 只在目标对象上触发（不是所有 UIView）
2. 只打前 N 次（计数器）
3. **测完立刻摘掉**，不要留在正式包里

## 七、给下次的一句话

> **透明度是「页面级」的属性，不是「视图级」的。**
>
> 「彻底透明」这种全局操作，在聊天页是美学，在列表页是灾难。
> 想让它安全，就不要整棵树遍历 —— 按**类名白名单**精确清理，
> 并且把白名单下沉到每一个 hook 里（因为清理可能发生在任何一个 hook 中）。
