## 〇、一句话

**「问号 + 拖不动」是两个不同的 bug，但根因是同一个：`use-after-free`。**

修完之后真机实测：搬一张卡 → 提示词 **210 字**；再搬一张 → **268 字**。

## 一、★★ 真凶：`fdmpc_move_in` 里的 use-after-free

### 1.1 有 bug 的写法

```c
int fdmpc_move_in(fdmpc_state *st, const char *key) {
    ...
    if (pc_list_remove(st->drawer, &st->drawer_n, key) != 0) return -1;
    //  ↑ 这个函数内部会 free(list[i])，而 key 往往就是 st->drawer[i] 本身

    if (pc_box_push(st, key) != 0) { ... }
    //  ↑ 拿**已释放的指针**去 strdup
}
```

### 1.2 为什么小窝测试全过、真机全错

| | 小窝 gcc | 真机 clang + malloc tcache |
|---|---|---|
| `free()` 之后内存 | **原样保留**，内容还在 | 立刻被**覆写**成 freelist 指针 |
| `strdup` 拿到的 | 恰好还是原来的 key | 垃圾字节 |

⇒ 小窝：42 条断言全过。
⇒ 真机：`box[]` 里存了垃圾 ⇒ 三件事同时发生：

```
① compose 找不到卡      → 「重算了系统提示词：0 字（容器 4 张）」
② 归一化补卡时 title 是垃圾 → 界面标题全是 "?"
③ 拖拽拿到的 key 是 nil   → 「拖回抽屉 (null) rc=0」
```

### 1.3 修法

```c
/* ★ 必须先复制，之后再全程用副本 */
char *kcopy = pc_strdup(key);
if (!kcopy) return -1;

if (fdmpc_where(st, kcopy) == 1) { free(kcopy); return -1; }
if (pc_list_remove(st->drawer, &st->drawer_n, kcopy) != 0) { free(kcopy); return -1; }
if (pc_box_push(st, kcopy) != 0) { pc_drawer_push(st, kcopy); free(kcopy); return -1; }
free(kcopy);
```

`fdmpc_move_out` 和 `fdmpc_delete_card` 是**同一个 bug**，一起修了。

> `fdmpc_delete_card` 原来的写法更明显：
> `pc_list_remove(..., key); pc_list_remove(..., key); int i = fdmpc_find(st, key);`
> 两次 remove 已经把它 free 了，后面还拿它去 find。

### 1.4 为什么原来的自检抓不到

原来的断言是「move_in 之后立刻 compose」—— 那一刻内存还没被覆写，所以**永远通过**。

新加的断言（编号 101~105，特意跳开避免撞号）**主动灌垃圾**：

```c
fdmpc_move_in(&u, FDMPC_T_SUGGEST);
/* ★ 关键：用 200 个同尺寸块把 tcache 灌满，逼它复用刚 free 的那块 */
for (int k = 0; k < 200; k++) {
    char *junk = malloc(32);
    if (junk) { memset(junk, 'X', 31); junk[31] = '\0'; }
    free(junk);
}
/* 现在再检查 */
assert(box[0] == "suggest");        /* 有 bug 时这里是 "XXXXXXXX..." */
assert(compose 里有 "【追问建议】");
```

同理测 `move_out`。

### 2.3 「全换问号」的三重兜底

就算 UAF 修好了，也不想再看到一次 "?"。加了三个保险：

**① 内置卡标题由「类型」决定，不读存档**

```objc
if (fdmpc_is_builtin_type(card->type)) {
    c.titleLbl.text = PUTypeTitle(card->type);   // "回复建议"/"音乐"/"富文本"
} else {
    c.titleLbl.text = PUSafe(@"title", card->title);
}
```

存档里 title 写坏了也影响不到内置三张。

**② `PUSafe()` 三级转换**

```objc
① [NSString stringWithUTF8String:]      // 正常路径
② [[NSString alloc] initWithData:...]   // 兜底（对截断序列宽容些）
③ 逐字节转，坏的换 '?' + **打日志**     // 走到这里说明存档脏了
```

**③ 存档体检：可疑就丢弃**

```objc
if ([js containsString:@"\"\""]) suspicious = YES;   // v70 的 sprintf bug 特征
/* 再过一遍：box/drawer 里 key 长度 < 2 一律当脏数据 */
```

发现可疑 ⇒ 备份成 `.bad` ⇒ 回默认卡片池 ⇒ 立刻覆盖写干净的。

**④ 字体不用 weight API**

```objc
// ❌ iOS 15 上对中文 fallback 可能失败
[UIFont systemFontOfSize:15 weight:UIFontWeightMedium]
// ✅
[UIFont systemFontOfSize:16]
```

## 五、给下次的三句话

> **1. 小窝测试全过 ≠ 真机没问题，尤其是内存 bug。**
> gcc 不覆写刚 free 的内存，clang + tcache 会立刻覆写。
> **测 UAF 必须主动灌垃圾**（分配 200 个同尺寸块再检查），
> 否则断言永远是"通过"的 —— 这种假安全感比没有测试更危险。

> **2. 「一个症状」背后可能是「一串 bug」。**
> 问号、拖不动、0 字、null —— 四个症状，**同一个根因**。
> 修对根因之后四个一起好了。

> **3. 字符串计数别用 `strlen`。**
> 中文 3 字节/字，`strlen("音乐")` = 6 但只有 2 个字。
> 界面上一律 `NSString.length`。
