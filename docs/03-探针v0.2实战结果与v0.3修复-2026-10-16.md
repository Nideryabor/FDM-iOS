## 〇、三句话

1. **探针成功注入并抓到了全部核心答案** —— iOS 的设置**确实走 MMKV**，实例是 **`mmkv.default`**，键是**裸名**，值是 **NSData(JSON 序列化)**。
2. **但探针把 App 搞崩了** —— 登录后宿主按用户 UUID 疯狂创建 MMKV 实例（**11961 次**），而探针每次都写盘 + NSLog ⇒ 性能雪崩 ⇒ 崩溃重启。
3. **v0.3 已修复**：去重 + 内存缓冲 + 零宿主调用 + 重入保护；顺带把 42 KB 的服务端下发 blob dump 出来。

## 一、⭐ 核心答案（v0.2 战果）

### 1.1 MMKV 实例

```
★ MMKV 取默认实例 defaultMMKV → mmkv.default
★ MMKV 实例创建  mmkvWithID: 1f4f3f9c-****-****-****-************   ← 用户级！
```

| 实例 | 含义 |
|---|---|
| **`mmkv.default`** | App 全局设置（privacy / app.* / serverValues） |
| **`<用户 UUID>`** | **按用户分桶**（对应泛型类 `MMKVWrapper<AppModels.User?>`） |

### 1.2 ⭐ 设置**确实走 MMKV**（推翻静态推断）

v0.2 日志实锤 —— 全部 9 个键，全写进 `mmkv.default`：

```

app.update.showKey                     = NSData 4B  6e756c6c          ("null")
app.colorScheme                        = NSData 8B  2273797374656d22  ("\"system\"")
app.welcome.showed                     = NSData 5B  66616c7365        ("false")

```

**值的编码规律（关键）**：
| Swift 类型 | 存储字节 | 例 |
|---|---|---|
| Bool | 裸文本 `true` / `false` | `74727565` = `true` |
| String | **带 JSON 引号** | `2273797374656d22` = `"system"` |
| Int | 裸数字 | `33` = `3` |
| 大对象 | JSON 序列化 blob | 42 KB |

> ⇒ **要写值，必须按同一规则编码**（否则宿主解码失败）。

### 1.3 ⭐ `app.ab.serverValues` = 服务端下发设置的本地 blob（42,522 B）

这是**最关键的一条**：iOS 把整套服务端设置存成**一个 42 KB 的 blob**，键名 `app.ab.serverValues`。

对应 Swift 结构：
```
_TtGCs18_DictionaryStorageSSVVOO13DeepSeek_Chat12ServerModels8Response14ClientSettings7Setting_$
_TtGCs18_DictionaryStorageSSVVOO13DeepSeek_Chat9AppModels8Response14ClientSettings7Setting_$
```

⇒ **iOS 与安卓的差异确认**：
| | 安卓 | iOS |
|---|---|---|
| 服务端设置落地 | **每键**一个 `kv_settings_<key>` | **一个大 blob** `app.ab.serverValues` |
| 本地覆盖方式 | 写单键覆盖 | **需要改 blob**（或覆盖读取层） |

## 二、💥 崩溃复盘

```
15:30:27  pid=4630   第 1 次启动（日志 1~7606 行）
          ← 登录后开始 mmkvWithID 暴雨
15:31:01  pid=4637   第 2 次启动（日志 7607 行起）★ 中间崩过一次
          之后: mmkvWithID: 1f4f****-...  × 11961   直到日志结束
```

**11961 次 `mmkvWithID: <用户UUID>`** —— 登录后宿主按用户 ID 反复取实例。

### 探针犯的三个错

| # | 错误 | 后果 |
|---|---|---|
| 1 | `my_*` 里调 `MMKVID(self)` → `[self mmapID]`（**宿主方法**） | 在 MMKV 锁内又碰 MMKV；违反"Hook 内不调宿主方法"铁律 |
| 2 | `mmkvWithID:` **无去重**，每次都 NSLog + 写文件 | 11961 次重 IO ⇒ 主线程/看门狗超时 |
| 3 | 所有 Hook 都在调用线程同步做文件 IO | 雪上加霜 |

> ⚠️ 这不是 DeepSeek 的 bug，是探针自己太重。**注入类探针的铁律：Hook 内只做 O(1) 内存操作。**

## 三、v0.3 修复清单

| 修复 | 做法 |
|---|---|
| **重入保护** | `__thread int gDepth`，Hook 重入时直接走原 IMP |
| **零宿主调用** | 删除 `MMKVID()`；只用指针地址 `%p` 或安全类型判断，**绝不调 `description`** |
| **实例 ID 去重** | `NSMutableSet gSeenIDs`：11961 次调用 → 只记首次（约几十条日志） |
| **异步刷盘** | Hook 内只 `append` 到内存 buffer；后台 `dispatch_source` 每 2 s 刷一次 |
| **重活后台化** | 类 dump / KV dump 全在 `QOS_CLASS_UTILITY` 队列，定时触发（3s/12s/45s/100s） |
| **NULL 保护** | `DumpOneMMKV` 检查方法 IMP 非空，防野指针崩溃 |
| **blob 立即落盘** | 抓到 `app.ab.serverValues` 时**异步**写 `fdm-blob.bin`（不错过） |

### v0.3 产出（4 个文件，App 沙盒 `Documents/`）

| 文件 | 内容 |
|---|---|
| `fdm-probe.log` | 精简事件日志（去重后） |
| `fdm-kv.txt` | **主动 dump 的 key → value 全表**（default + 所有收集到的实例） |
| `fdm-blob.bin` / `fdm-blob.json` | **`app.ab.serverValues` 原始 42 KB + JSON 美化** ★ |
| `fdm-classes.txt` | 宿主相关类的方法 / ivar 结构 |
