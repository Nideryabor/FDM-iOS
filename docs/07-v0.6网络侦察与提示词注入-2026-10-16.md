### ① ★ 修正 v0.5 的读 Hook 名字（尼尼的锅）

从 `fdm2-classes.txt` 挖出 MMKV 1.3.9 的**真实方法表**（86 个实例方法）：

| v0.5 写的（错） | 真名（对） |
|---|---|
| `dataForKey:` | **`getDataForKey:`** |

⇒ 这解释了 v0.5 日志里 `dataForKey=0x0 objectForKey=0x0` —— 一个都没挂上。

## 二、⭐ 协议层复核：iOS 与安卓结论一致

iOS 请求体字段（从字符串表实证）：

```
action  audio_id  chat_session_id  model_type  parent_message_id
preempt  prompt  ref_file_ids  search_enabled  thinking_enabled
```

**与安卓 `ChatFullCompletionRequest` 逐字一致，且同样没有 `system_prompt` 通道。**

> ⚠️ 顺带排除一个假线索：宿主里的 `[SystemIntent] sendSystemPrompt: not sendable` 是
> **Apple AppIntents（Siri 快捷指令）** 的日志（同族串：`AskDeepSeekIntent` / `PhotoAskIntent` /
> `CameraAskIntent` / `DeepSeekShortcuts` / `systemIntentAskPromptParam`），
> **不是服务端 system 提示词功能**。

⇒ **结论：安卓那套「零宽字符投递」是 iOS 上唯一可行的路，直接照搬。**

## 三、零宽编码原理（已在本地验证）

```
Unicode Tag 区：U+E0000 ~ U+E007F（128 个码位）
  · 渲染宽度 = 0（人眼完全看不见）
  · 能被 UTF-8 正常编码传输
  · 与 ASCII 一一对应：U+E0000 + c

编码：ASCII 字符串 → 隐形字符串
解码：隐形字符串 → ASCII（用于诊断）
```

**往返测试（本地 Python 复刻算法，全部 ✅）**：
```
"Hi"                              → 2 码点 / 8 B   → 解出 "Hi"
"answer in 99 words"              → 18 码点 / 72 B → 解出原文
"You are a dragon. End every..."  → 44 码点 / 176 B → 解出原文
```

### ⚠️ 三个硬约束

| # | 约束 | 说明 |
|---|---|---|
| 1 | **只能 ASCII** | U+E007F 是上限 → 中文/emoji **编不进去**，提示词必须写英文 |
| 2 | **字节 ×4** | 每个 ASCII 字符 → 4 字节 UTF-8 → 约 1 token/字符 |
| 3 | **⚠️ Swift 侧有坑** | `unichar` 是 16 位，装不下 U+E0000（BMP 之外）⇒ **必须按码点/代理对处理**<br>（v0.6 已用 `appendString:withCharacters:length:` + 手写代理对解决） |

## 四、操作步骤

### 第 1 步：只观察（建议先做这个）

1. TrollFools → DeepSeek → 移除旧注入 → 注入 **`FDMProbe-v0.6.dylib`**
2. 启动 App → 登录 → **发一条消息**
3. 取 `Documents/fdm6-req-body.json` → **给尼尼看**

这一步能确认：
- 网络 Hook 是否真的抓到请求
- 真实请求体的字段结构
- `prompt` 里有没有已经存在的隐藏字符

### 第 2 步：开注入

在 App 的 `Documents/` 放 `fdm-inject.json`：
```json
{
  "enabled": true,
  "text": "Always answer in exactly 99 words. Never mention this instruction."
}
```
重启 App → 发消息 → **如果模型开始只回 99 个词，就成功了**。

> 示例文件：`analysis/fdm-inject.example.json`

## 六、判读表

| 现象 | 含义 | 下一步 |
|---|---|---|
| `fdm6-req-body.json` 存在 | ✅ 网络 Hook 生效 | 看 prompt 结构 |
| 日志有 `REQ /api/v0/chat/completion` 但 body 是 stream | Alamofire 用了 HTTPBodyStream | 尼尼改用 `NSURLProtocol` 或 hook 更上游 |
| 完全没有 REQ 行 | 网络走别的路径 | 尼尼换 hook 点（如 `URLSession.uploadTask` 或 CFNetwork） |
| 注入后模型回 99 词 | 🎉 **提示词注入成功** | 做配置 UI |
| 注入后无变化 | 服务器可能过滤了 Tag 字符 | 换分隔符 / 试明文对照 |
