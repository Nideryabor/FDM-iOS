## 二、★ 最重要的方法论：状态驱动

### 2.1 为什么追"谁覆盖的"失败了

诊断链证明了三件事：

```
① 渲染逻辑对       → 属性 4 项 → 6 项
② 数据是活的       → [survive] 50ms 后属性 5 项、有颜色、内容一致
③ 思考块能保持彩色 → 说明我们的渲染本身没问题
```

但回复块就是不变。而调用栈里的符号**全被剥离了**（只有 `DeepSeek Chat + 6012008` 这种），
根本不知道是谁。

### 2.2 换打法：只问结果，不问过程

```objc
/* 每 0.5 秒扫一遍可见视图树 */
while (遍历) {
    if (控件.attributedText 里还带 '<') {
        setAttributedText(渲染它);      // 现场重算
    }
}
```

**真机结果：**
```
[ensure] ★ 巡检修正 ...ResponseMarkdownAdapter_ 74→55 字
[ensure] ★ 巡检修正 ...ResponseMarkdownAdapter_ 293→164 字
```

正是那个显示裸标签的回复块，被持续修正 ⇒ 稳住了。

### 2.3 这个套路已经用了三次

| 功能 | 函数 | 思路 |
|---|---|---|
| 液态玻璃 | `EnsureAttached` | 每 1.2s 看玻璃还在不在 |
| 对话气泡 | `BubbleEnsureAll` | 每 1.2s 看底色对不对 |
| **富文本** | `FDMStripEnsureRichTick` | **每 0.5s 看属性对不对** |

> **规律：事件驱动在"宿主自己会重排"的场景下必然漏。
> 状态驱动天然免疫，因为它只看最终结果。**
