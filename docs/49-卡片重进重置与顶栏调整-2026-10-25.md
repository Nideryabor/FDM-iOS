## 〇、一句话

**我自己的"坏存档检测"把好存档当坏了。**

`[js containsString:@"\"\""]` 想抓 v70 那个 bug 留下的 `""music`，
但**正常存档里也有 `""`** —— 内置三张卡的正文本来就是空的（`"tx":""`）。

⇒ 每次读到「有内置卡且正文空」的存档 → 判"可疑" → 丢弃 → **UI 重置**。

---

## 一、错误的检测

```objc
// v72（错的）
BOOL suspicious = NO;
if ([js containsString:@"\"\""] || [js containsString:@"[\"\""]) suspicious = YES;
```

想抓的特征：`"drawer":[""music", ...]`（v70 的 sprintf bug）

但正常存档长这样：

```json
{
  "nextId": 1,
  "drawer": ["suggest","music","richtext","textsrc"],
  "box": [],
  "cards": [
    {"k":"suggest","t":"suggest","ti":"回复建议","tx":""},
    //                                              ↑↑ 这里就有 ""
```

**内置三张卡的正文本来就是空的**，`"tx":""` 是合法的。
我的检测一看到 `""` 就判坏 ⇒ 每次进页面都重置。

---

## 二、正确做法：不猜字符串，看解析结果

```objc
// v73（对的）
BOOL suspicious = NO;
int rc = fdmpc_from_json(&_st, js.UTF8String);   /* ★ 直接解析，让归一化干活 */
if (rc != 0) {
    suspicious = YES;
} else {
    /* 归一化之后仍然有「key 少于 2 字符」的，只能是真的脏了 */
    for (size_t i = 0; i < _st.box_n; i++)
        if (!_st.box[i] || strlen(_st.box[i]) < 2) suspicious = YES;
    for (size_t i = 0; i < _st.drawer_n; i++)
        if (!_st.drawer[i] || strlen(_st.drawer[i]) < 2) suspicious = YES;
    if (_st.count < 4) suspicious = YES;    /* 内置三张+源卡都没了 ⇒ 真坏 */
}
```

### 为什么这样就够了

`fdmpc_from_json` 内部已经跑了 `pc_normalize()`：

| 归一化规则 | 顺手解决的问题 |
|---|---|
| 列表有 / 卡片表没有 → 补卡 | v70 那种 `""music` 的孤儿 key 会被补成一张（无害） |
| 类型不认识 → 丢掉 | 脏类型自动清理 |
| 内置三张 + 源卡必须存在 | **`_st.count < 4` 就是真坏的判据** |
| 同 key 不许同时在两个列表 | 幽灵卡消失 |

⇒ **解析成功 + 归一化干净 = 可以信**。不需要在外面再猜一遍字符串。

## 三、顶栏按主人要求调整

```
左 = 返回      ← 原来是"重置"
右 = 重置      ← 原来是"新建"
```

### 3.1 返回键为什么要自己做

因为我们设了 `self.navigationItem.leftBarButtonItem`，
**系统的返回按钮会被顶掉**。所以自己做一个：

```objc
- (void)onBack {
    if (self.navigationController &&
        self.navigationController.viewControllers.count > 1) {
        [self.navigationController popViewControllerAnimated:YES];
    } else if (self.navigationController) {
        [self.navigationController dismissViewControllerAnimated:YES completion:nil];
    } else {
        [self dismissViewControllerAnimated:YES completion:nil];
    }
}
```

> 三层兜底：正常 push 进来的 → pop；被 modal 包了一层 → dismiss nav；
> 连 nav 都没有 → 直接 dismiss 自己。

### 3.2 「新建」移到哪儿了

移到**「容器」分组的表头右侧**（`＋ 新建`）。

```
容器（进提示词）· 2 张 — 按住左边 ≡ 拖动        ＋ 新建
```

好处：新建的卡会直接进容器，按钮放在容器表头上语义也顺；
而且不用再挤导航栏。

```objc
- (UIView *)tableView:viewForHeaderInSection:(NSInteger)sec {
    ...
    if (sec == 0) {   /* 只在容器分组放"＋ 新建" */
        UIButton *b = [UIButton buttonWithType:UIButtonTypeSystem];
        [b setTitle:@"＋ 新建" forState:UIControlStateNormal];
        [b addTarget:self action:@selector(onAdd) ...];
    }
}
```

## 六、给下次的三句话

> **1. 别用「字符串包含」去猜数据结构好不好。**
> 正常数据里也会出现你以为是"坏特征"的子串
> （这里的 `""` 既是 v70 bug 的症状，也是空正文的合法表示）。
> **解析 + 校验状态**永远比猜字符串可靠。

> **2. 设了 `leftBarButtonItem` 就等于删掉了系统返回键。**
> 要自己实现 pop，而且得考虑 modal 包裹、nav 缺失的情况（三层兜底）。

> **3. 一个"防御性代码"本身可能就是 bug 来源。**
> 我加 `suspicious` 检测是为了保护数据，
> 结果它每进一次页面就把用户的卡片清一次 ——
> **比不保护还糟**。（保护性代码也要有测试覆盖。）
