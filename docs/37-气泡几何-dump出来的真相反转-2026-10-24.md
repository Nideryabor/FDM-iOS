## 〇、一句话

**上一轮 12 个版本全跪，是因为「气泡容器」从头到尾都选错了。**
真机 dump 一次就看清了：**AI 气泡的最外层是 `AgentMessageCell`（414x303），
而真正该画底的是它肚子里的 `AgentFragmentsView`（366x235）——
两者面积差 1.46 倍，中间还夹着一条 36px 的操作按钮条。**

## 一、这一轮做了什么

### 1.1 先按铁律来：只 dump，不画

新建 `src/FDMProbe5/FDMBubbleDiag.m`：

- 独立开关 `fdm-bubble.json` 里的 `{"diag": true}`
- 与气泡功能开关（`on`）**完全解耦**，功能关着也能诊断
- **一个字都不改**：不碰 backgroundColor / cornerRadius / mask / layer，
  不 addSubview，不 swizzle 任何 setter
- 输出 `Documents/fdm-bubble-geom.txt`

### 1.2 ★ 踩了两个坑，都是「在错误的时间读」

| 版本 | 做法 | 结果 |
|---|---|---|
| v1 | hook `layoutSubviews`，在里面读 `layoutManager.usedRectForTextContainer:` | **SIGBUS ×2**，一个字节都没写出来 |
| v2 | 改成 `NSTimer` 每 0.8s 巡检（跑在主 runloop） | ✅ 成功，没崩 |

**v1 为什么崩**：宿主在 `setAttributedText:` 里（`[strip]` 日志刚打完字），
此时 `textStorage.length` 和 `layoutManager` 的 glyph 数**不一致**，
`usedRect` 内部按 glyph 索引访问 ⇒ 越界 ⇒ `SIGBUS=10`。

**关键认知**：`SIGBUS` 不是 Objective-C 异常，`@try/@catch` **完全抓不住**。
所以「包在 try 里就安全」这个念头是错的。

**v2 为什么对**：NSTimer 回调跑在主 runloop 的正常上下文里，
那时 `setAttributedText` 早已返回、布局也已收敛。

> 这条其实是文档 36 铁律的延伸：
> 不只是「先 dump 再动手」，还有「**在回调里读别人正在改的东西 = 自找**」。

### 1.3 还加了 TextKit 读取守卫

`TextKitReadable()` 在真正读之前检查四件事：

1. `textStorage` 非 nil 且 `length > 0`
2. `textContainer` 非 nil
3. `layoutManager` 存在且 `numberOfGlyphs > 0`
4. **`glyphs <= textStorage.length`** ← 状态收敛的判据，不满足就不读

宁可这一轮跳过，也不赌。

## 二、★★★ dump 出来的真相

### 2.1 AI 侧完整结构（`AgentMessageCell` 414x303）

```
AgentMessageCell            414x303   bg=#0F0F0F/1.00  corner=0  clip=0
└─ UIView                   414x303
   └─ AgentMessageView      414x303   bg=nil  corner=0
      └─ UIView             (16,12) 374x279
         └─ UIView          (8,0) 366x279
            ├─ AgentFragmentsView      366x235   ← ★ 文字容器
            │  ├─ AgentGroupView       366x29
            │  └─ ResponseFragmentView 366x196
            ├─ MessageLoadingView      0x0 (hidden)
            └─ AgentMessageOperationBar 366x36 @ y=243  ← 按钮条
```

### 2.2 三个反直觉的事实

**① AI 侧有最外层类，而且它有底色**

文档 36 说「AI 气泡没有单独的类」—— 那是**错的**。
`DeepSeek_Chat.AgentMessageCell` 就是，而且它自己 `bg=#0F0F0F`（不透明的深色）。

但注意：这是 **cell 的底色**，不是气泡底。整行都是这个颜色。

**② 宿主的气泡确实「没有圆角、没有独立底色」**

树里 15 个节点，`corner` 全是 0，`bg` 全是 nil —— 除了 Cell 自己那层 #0F0F0F。
所以「改气泡」不是改已有的底，而是**画一个新的底**。这条文档 36 说对了。

**③ 而且 `clip=0` 一路到底**

`AgentMessageCell` / `AgentMessageView` / 那两层 UIView / `AgentFragmentsView`
**全部 `clipsToBounds=0`**。

⇒ 这意味着：在 `AgentFragmentsView` 上插一个 `zPosition=-1` 的 CALayer，
**即使尺寸超出也不会被裁掉**。上一轮担心的「被裁」不存在。

### 2.3 尺寸账（关键）

| 项 | 值 |
|---|---|
| Cell | 414 x 303 |
| AgentFragmentsView | 366 x 235（在 Cell 坐标里 `(24,12)`）|
| OperationBar | 366 x 36（在 Cell 坐标里 `(24,255)`）|
| 文字真实包围盒 | `(24,15) 362.4 x 232` |

**算一下**：
- `235 + 8 + 36 = 279`（= 内层 UIView 的高度），严丝合缝
- Cell 303 - 279 = 24（上下各 12 的 padding）

**如果直接铺满 Cell**：414x303 = 125,442 px²
**如果只包 AgentFragmentsView + padding**：(366+28) x (235+18) = 394 x 253 = 99,682 px²

⇒ 铺满 Cell 会**多出 26%**，而且**把 36px 的操作按钮条也圈进去了**。

**这就是上一轮「蓝色大方块、文字只占左上角」的真正原因。**

### 2.4 正确的画法

```
气泡底 = AgentFragmentsView.bounds 外扩 (padX, padY)
        在 AgentFragmentsView 自己的坐标系里：
        (-14, -9)  366+28 x 235+18  即 394 x 253
        cornerRadius = 18
        zPosition    = -1
```

因为一路 `clip=0`，超出 AgentFragmentsView 边界的 14/9 不会被裁。

## 四·补、落地实现时又抓出两个 bug

dump 拿到真相之后换成新锚点，**第一次装上去还是不对**，
主人反馈「点击一些对话又不对了」。查日志，两个都是**逻辑 bug，不是猜错**：

### Bug A · 去重键里没有尺寸

```objc
// 原来
NSString *stamp = [NSString stringWithFormat:@"%d|%u|%.1f|%d|%d",
                   gMine.fill_enabled, gMine.fill_argb, gMine.corner, ...];
if ([stamp isEqualToString:prev]) return;
```

气泡住在**复用 cell** 里，复用流程是：

```
① 显示 67x46 的短消息  → 画 67x46 的底，stamp = S
② 滑走，cell 复用给 319x228 的长消息
③ layoutSubviews 又调  → 配置没变，stamp 还是 S ⇒ 直接 return
④ 结果 319x228 的视图上挂着 67x46 的底色
```

⇒ stamp 必须带 `%.1fx%.1f`（锚点 bounds）。
而且还要带 `%p`（锚点对象地址）—— 复用可能重建锚点对象，
container 不变、尺寸碰巧一样时，新锚点会一个像素都不画。

### Bug B · 用户侧 hook 了两个类，同一锚点被处理两遍

`UserBubbleView` 和 `UserRequestBubbleView` 都在白名单里：

```
UserRequestBubbleView.layoutSubviews → FindBubbleAnchor 找到 UserBubbleView → 填一次
UserBubbleView.layoutSubviews        → FindBubbleAnchor 返回自己      → 又填一次
```

日志里 `我：底色 (0,0 67x46)` **一字不差打了两次**，就是证据。

⇒ 只 hook 最外层容器（`UserRequestBubbleView`），
锚点仍然去肚子里找 `UserBubbleView`。

### 加了一层巡检兜底（沿用玻璃那套 EnsureAttached 思路）

```objc
static NSHashTable *gAnchors;   // 弱引用，锚点释放自动消失

每 1.2s：
  对每个登记过的锚点
    · 不在视图树上 → 跳过
    · 有 fill layer 但 frame ≠ bounds → 修正 frame / 夹紧圆角
    · 压根没有 fill layer → 往上找该被 hook 的容器，重走 ApplyStyleTo
```

日志证据（正常态）：

```
11:37:27.139 [D][ui] [bubble] 巡检修正 1 处（复用/尺寸漂移）
11:37:28.792 [D][ui] [bubble] 巡检修正 1 处（复用/尺寸漂移）
```

**stamp 去重负责省 CPU，巡检负责「结果一定对」——两道防线缺一不可。**

### 最终实测日志

```
我：底色 (0,0 67x46)   r=18.0 / 容器 67x46      ← 短消息，严丝合缝
我：底色 (0,0 321x228) r=18.0 / 容器 321x228    ← 长消息
对方：底色 (0,0 366x227) r=18.0 / 容器 366x227
```

主人压力测试（猛滑 / 点不同消息 / 切会话 / 长短消息混合）：**一切正常**，
崩溃计数停在 4（全是诊断阶段旧账，这一版零新增）。

## 五、给下次的三句话

> **1. dump 一次胜过 12 个版本。** 这次是真的。
> 从决定「先只 dump」到拿到几何，一共 40 分钟（含两次 SIGBUS 的代价）。

> **2. `SIGBUS` 不是异常，`@try` 救不了你。**
> 唯一解法是**不要在别人改东西的时候读**，或者读之前先把状态检查一遍。

> **3. 「最大最外层」往往不是你要的那个。**
> `AgentMessageCell` 414x303 看起来很像个气泡，其实它是一整行 + 按钮条。
> 真正的气泡是肚子里那块 366x235。
