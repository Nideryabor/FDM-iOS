## 二、修的两个真隐患

### 隐患 A：口令拼进了**远端**命令行（高危）

```bash
# tools/dep.sh:27 旧写法（deploy.sh / elikit.sh / dep-troll.sh 同样）
"cat > /tmp/_s.sh && echo '$PW' | sudo -S -p '' sh /tmp/_s.sh"
```

`$PW` 在**本地**展开后被拼进发到设备的命令串 ⇒ 执行那一两秒，
设备上 `ps aux` 就能看到明文。**任何能跑 `ps` 的进程都能看到，包括宿主 App 自己。**

### 隐患 B：`sshpass -p "$PW"` 让口令出现在**本机** argv

本机 `ps aux` / `/proc/<pid>/cmdline` 一样能捞到。

---

## 三、改成了什么

### 3.1 `_env.sh` 统一出口：`export SSHPASS="$PW"`

所有脚本从 `sshpass -p "$PW"` 改成 **`sshpass -e`**（从环境变量读）。
⇒ 本机 argv 里只剩 `sshpass -e ssh ...`，口令只存在于进程环境（`/proc/<pid>/environ`，只有同用户可读）。

> 一次性替换：`sed -i 's/sshpass -p "\$PW"/sshpass -e/g' tools/*.sh`
> 附带检查：**每个用 `sshpass -e` 的脚本都必须 `source _env.sh`**，否则 SSHPASS 没人给 → 静默失败。
> 已逐个核对：8 个脚本全都有。

### 3.2 `sshsu` / `ssu`：两步走，口令只走 stdin

```bash
sshsu() {
    local tmp="/tmp/_fdm_$$.sh"
    # ① 脚本内容走 stdin 落到临时文件（内容里不含口令）
    printf '%s\n' "$1" | sshpass -e ssh $SSH_OPTS "$USER@$HOST" "cat > $tmp" 2>&1 \
        | grep -v "^Warning:" | grep -v "^Permanently"
    # ② 口令单独走 stdin 喂 sudo -S，argv 里只剩 "sudo -S -p '' sh /tmp/xxx"
    printf '%s\n' "$PW" | sshpass -e ssh $SSH_OPTS "$USER@$HOST" \
        "sudo -S -p '' sh $tmp; rm -f $tmp" 2>&1 \
        | grep -v "^Warning:" | grep -v "^Permanently" | grep -v "^Password:"
}
```

> 为什么不用「口令 + 脚本挤同一条 stdin」的省事写法？
> `sudo -S` 从 stdin 读口令时**可能多读**（缓冲），脚本第一行就会被吞掉。
> 分两次连接虽然多 ~200ms，但语义确定、不赌 sudo 的实现细节。

### 3.3 备份脱敏

`backups/pre-env-fix/{dep,deploy,free,iphone}.sh` 里的明文口令
→ 全部替换成 `__已脱敏·见_env__`，四个文件 `bash -n` 语法复查通过。

## 六、`.env` 不会进库（双保险）

主人明确要求「这个 .env 不要交上去」。查证结果 + 加固：

### 现状（已经是干净的）

| 检查 | 命令 | 结果 |
|---|---|---|
| `ios-port` 在 git 眼里 | `git status --short ios-port` | 空（无可提交内容） |
| git 跟踪了几个 ios-port 文件 | `git ls-files ios-port \| wc -l` | **0** |
| `.env` 被谁挡住 | `git check-ignore -v ios-port/.env` | `.gitignore:172:/ios-port/` |
| 暂存区 | `git diff --cached --name-only` | 无 `.env` |
| 已跟踪文件 | `git ls-files \| grep -iE '\.env($\|\.)'` | **0 个** |
| 全历史（含所有分支） | `git log --all --name-only` | **0 次** |
| git 对象库 | `git rev-list --all --objects` | 没有 `.env` 的条目 |

### 加固：第二道不依赖目录的锁

`/ios-port/` 那条规则一去掉（比如哪天想「只提交源码」），`.env` 就裸了。
所以 `.gitignore` 里另加一组**不依赖目录**的规则：

```gitignore
.env
.env.*
.env.bak*
*.env.bak*
!.env.example        ← 模板放行（只有占位符）
```

**模拟验证**：手动注释掉 `/ios-port/` 后重查 ——
`ios-port/.env` 和 `ios-port/.env.bak-1025-ip7` **仍然被挡住**，
`.env.example` 恢复可入库。

> 小注：目录级忽略生效时，`!.env.example` 的放行**看不见效果**
> （git 不会进被排除的目录），但目录规则一去掉它就起效 —— 这正是双保险的意义。

### 护栏升级：⑤ git 侧四条

`tests/security/test_secrets.sh` 新增（现在共 10 项）：

| 项 | 查什么 |
|---|---|
| 5a | `git ls-files` 里 0 个 `.env` 系 |
| 5b | 暂存区 0 个 `.env` 系 |
| 5c | 全历史 0 个 `.env` 系（有就提示「需要改写历史」） |
| 5d | `.env` 必须被某条 ignore 规则命中（并打印是哪条） |

**检测逻辑自证**：在 `/tmp` 建个假仓库，故意 `git add -f .env` + 提交，
⑤ 的 grep 立刻抓到「已跟踪」和「历史里有」两条 —— 说明护栏不是摆设。

## 七、关于「内网 IP 别怕」

收到，这条我不再当风险提：`192.168.1.8:2222` 是内网地址，
写在文档/`APP_DOCS` 里不构成泄露（除非哪天做端口转发到公网）。

**但口令强度那条我保留意见**：内网只降低「被人扫到」的概率，
不降低「一旦被扫到就是灾难」的后果 —— 弱口令 + `sudo` 无限制，两样叠加
在任何暴露面下都是最高危组合。换不换由主人定。
