## 〇、一句话

**`class_getInstanceMethod` 会沿继承链返回父类的 Method，
改它 = 改父类方法表 = 全 App 所有子类中招。**

这条在 docs/36 §2.3「坑 1」里我**自己写过一遍**，这次又踩了。

---

## 一、症状：满屏都是头像

真机日志（第一版）：

```
[assistant] 给 UILayoutContainerView 插入头像（bounds 414x736）   ← 整个屏幕
[assistant] 给 UIView 插入头像（bounds 414x736）
[assistant] 给 UIImageView 插入头像（bounds 414x736）
[assistant] 给 UILabel 插入头像（bounds 208x25）
```

主人反馈：「出现重复的多个头像」。

---

## 二、根因

```objc
// 错的
Method m = class_getInstanceMethod(cls, @selector(layoutSubviews));
IMP orig = method_getImplementation(m);
method_setImplementation(m, mine);      // ← m 可能是 UIView 的！
```

`AgentMessageView` **自己没有实现 `layoutSubviews`**，
`class_getInstanceMethod` 就沿继承链找到 **UIView 的实现**并返回，
`method_setImplementation` 改的是 **UIView 的方法表**
⇒ 所有 UIView 子类的 `layoutSubviews` 全都跑进我们的 hook
⇒ 每个视图上都被插了一个头像。

### 正解（docs/36 已写，这次照做）

```objc
if (class_addMethod(cls, sel, (IMP)MyHook, types)) {
    // 加成功 = 本类原本没有 ⇒ 以后只影响本类
    // 注意：MyHook 里必须手动转发给父类实现
    return;
}
// 加不成功 = 本类已有实现 ⇒ 才可以安全替换
IMP orig = method_getImplementation(m);
method_setImplementation(m, mine);
```

修完日志：

```
[assistant] DeepSeek_Chat.AgentMessageView 本类无 layoutSubviews ⇒ class_addMethod（安全）
```

### 顺手把气泡也加固了

气泡那边目前没炸，纯粹是因为 `AgentMessageCell` / `UserRequestBubbleView`
**恰好**自己实现了 `layoutSubviews`。宿主一改版就可能不实现 ⇒ 一夜之间满屏乱画。

⇒ `FDMBubble.m` 的 `HookLayout()` 也改成先 `class_addMethod`，
并把 hook 主体抽成 `BubbleLayoutBody()` 两条路径共用。

### 3.2.1 ★ 静态交叉引用（ADRP+ADD）—— 铁证

光看 ivar 表和运行时扫树还不够硬。主人问「是不是真的不能走安卓的路」，
那就把二进制翻开，数**谁引用了这几个类字符串**：

```bash
python3 analysis/xref.py "DeepSeek Chat" --find "<类名>"
```

| 类名字符串 | 位置 | **被代码引用次数** |
|---|---|---|
| `_TtCC13DeepSeek_Chat16AgentMessageView10AvatarView` | 0x101112e20 | **0** |
| `_TtCC13...InnerAvatarView` | 0x101112e60 | **0** |
| `DeepSeek_Chat.AvatarView` | 0x101112f20 | 1（见下）|
| `DeepSeek_Chat.AgentFragmentsView` | 0x101110b50 | **1** ✅ 对照组 |

### 那唯一 1 处引用是什么？

```
=== DeepSeek_Chat.AvatarView @ 0x101112f20  引用 1 处 ===
   代码 0x1005d44a0
```

看这个地址附近引用了哪些字符串：

```
[0x1010f7cf0] init(coder:) has not been implemented
[0x1010f8360] Fatal error
[0x1010fb8a0] init(frame:)
[0x101112ed0] DeepSeek_Chat.InnerAvatarView
[0x101112ef0] DeepSeek_Chat/AgentAvatarView.swift
[0x101112f20] DeepSeek_Chat.AvatarView
[0x101112f40] .../Cell/Views/AgentAvatarView.swift
```

**这是 `AgentAvatarView.swift` 里两个类自己的 `init(frame:)` 错误处理代码**
（`init(coder:) has not been implemented` + `Fatal error` + `init(frame:)`）。
也就是说，这唯一的引用来自**它们自己的初始化函数**，
不是任何外部控件在创建它们。

### 对照组说明问题

`AgentFragmentsView` 有 **1 处外部引用**（宿主在 cell 配置时按名字找它/建它），
所以它在运行时真的会出现 —— 我们 dump 时确实看到了它（366x415）。

而 `AvatarView` 的 0 处引用意味着：
**从 App 启动到退出，没有任何一行代码会说「创建一个 AvatarView」。**

### 3.2.2 结论（三重独立证据）

| 证据 | 结论 |
|---|---|
| ① runtime 类存在 | 类被编进了 App |
| ② `AgentMessageView` 的 ivar 表无 avatar 槽位 | 宿主没有保存它的地方 |
| ③ **类名字符串在代码中被引用 0 次** | **没有任何代码创建它** |

⇒ **iOS 宿主的助手头像是「编译进去了但完全没接线」。**

不是灰度能救的：
安卓那边是「有接线 + 灰度关掉」，把 `hide_assistant_avatar` 置 false 就能显示；
iOS 是**连接线都没有**，灰度开关根本不存在（二进制里搜不到 `hide_assistant_avatar` 这个键）。

所以「替换宿主头像的图」在 iOS 上做不到 —— **没有那个视图可以替换。**

### 3.3 对比安卓：为什么那边可以，这边不行

| | 安卓 | iOS |
|---|---|---|
| 宿主有没有头像视图 | ✅ 有 | ✅ 有（类在）|
| 有没有接线 | ✅ 有 | ❌ **0 处引用** |
| 灰度键 | `hide_assistant_avatar`（二进制里能搜到）| **搜不到这个键** |
| 修复方式 | 把灰度置回 false ⇒ 宿主自己显示 | **无解**，只能自己插 |

> 补充：iOS 二进制里 `hide_assistant_avatar` / `hideAssistant` / `hideAvatar`
> **一个都搜不到** —— 说明 iOS 侧压根没用这套灰度，
> 那两个 Avatar 类大概是 Android 端代码/设计稿的残留，编译进去但从未启用。

### 3.4 那就只剩「自己插」

但位置是**实测出来的，不是猜的**：

```
AgentMessageView  414x439
  └─ UIView        (16,12)  374x415
     └─ UIView     (8,0)    366x415
        └─ AgentFragmentsView 366x415   ← 正文
```

正文左边到容器左边 = **16 + 8 = 24px**
⇒ 头像 22px、x=1、y=12 ⇒ 右边缘 23 < 24，**一个像素都不压字**。

这三个数字被实测定死，所以**不进设置页**（让用户填只会填错）。

## 四、配置精简（按主人要求）

## 六·补、后续（2026-10-24 深夜 · 主人在新宿主 2.7.1 上复核）

这一节的结论在 **2.7.1** 上重新验证过，并且挖到了旧版 1.2.6 做对比。
完整报告见 **docs/40**。这里只记结论：

| 项 | 2.6.2 | 2.7.1 | 旧版 1.2.6 |
|---|---|---|---|
| `AvatarView` 类存在 | ✅ | ✅（运行时）| ✅ |
| 被代码引用 | **0 处** | 0 处 | **0 处** |
| `AgentMessageView` 有 `avatar` 字段 | ❌ | ❌ | ✅ **有** |
| 灰度键 `hide_assistant_avatar` | ❌ | ❌ | ❌ |

**⇒ iOS 的助手头像功能是「1.x 有、2.x 删了」，删得很干净，
连灰度开关都没留下。安卓那套「置 false 就显示」在这里完全用不了。**

另外补一条血案：尼尼试过「既然类还在，就自己 `alloc/init` 它」——

```
[av-probe] ═══ 尝试实例化 AvatarView ═══
===== CRASH signal=5 (SIGTRAP) =====
```

**Swift 类的 `init` 里有 `fatalError` 前置条件，外部裸 alloc 必然 trap。**
这条路封死，代码已删。

⇒ 只能用「自己插 UIImageView」的方案（本篇写的那个），2.7.1 上仍可用。

## 七、给下次的三句话

> **1. `class_getInstanceMethod` 返回的不一定是「本类」的实现。**
> 先 `class_addMethod`，加成功就完事；加不成功才 `method_setImplementation`。
> **这条我已经写进文档两次了，这次是第三次犯。**

> **2. 「有类」≠「有实例」。** 查不到实例就去看 ivar 表 ——
> 没有槽位就是真的没接线，别再花时间找灰度开关。

> **3. 实测出来的数字不要放进设置页。**
> 22px 是为了塞进 24px 的缝，让用户改成 40 只会压字。
