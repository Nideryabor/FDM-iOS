## 二、⭐ 玻璃：怎么从「完全没效果」做到「真机可用」

### 2.1 真机暴露的第一个问题：Instal 太晚

原来 `FDMGlassInstall()` 放在 **6 秒定时器**里：

```
dyld 加载 dylib → 宿主 main() → 宿主创建全部 UI → 渲染完成
                                  → 3.5s 我们 real_init
                                  → 6s 才装 hook          ← 太晚
```

⇒ 宿主「注入前就存在」的按钮永远拿不到玻璃。

**关键认知**：TrollFools 的 dylib 是**进程启动时 dyld 加载的**，早于 `main()`。
所以根本不存在“注入前就有的控件”——是我自己拖到 6 秒才装 hook。

### 2.2 三阶段注入（主人提的架构建议）

```
① 构造函数（dyld，早于 main）
   · 只 swizzle UIView.didMoveToWindow
   · 纯 objc runtime + C 数组，绝不碰 Foundation
   · hook 里只做一件事：把控件指针塞进定长缓冲区

② fdm_real_init（3.5s，Foundation 就绪）
   · 读配置、装其它 hook
   · FDMGlassEarlyFlush() 把缓冲区的控件补处理一遍

③ 之后（每 1.2s 巡检）
   · 处理早期队列 + 增量
   · 维护已叠的（检查 layer 是否还在树上）
```

真机日志证据：
```
[glass-early] 补处理 23/23 个早期控件
```

### 2.3 ⚠️ 构造函数里 swizzle 直接崩（血的教训）

第一版在构造函数里直接 `method_setImplementation`，**注入瞬间崩**。两个原因：

**坑 1：改到了父类的方法表**
```objc
Method m = class_getInstanceMethod(uiview, sel);   // UIView 若没自己实现
method_setImplementation(m, ...);                  // ← 拿到的是 UIResponder 的 Method
                                                   //   改的是【父类】方法表！
```
⇒ 所有 `UIResponder` 子类（含 UIKit 私有类）都会走到我们的 IMP ⇒ 立刻崩。

**正解**：先用 `class_addMethod` 尝试只在本类加：
```objc
if (class_addMethod(uiview, sel, (IMP)myHook, types)) {
    gOrig = class_getMethodImplementation(class_getSuperclass(uiview), sel);
    return;                        // 加成功 = 本类原本没有，转发给父类
}
gOrig = cur;                       // 本类已有 ⇒ 才安全替换
method_setImplementation(m, myHook);
```

**坑 2：dyld 阶段 UIKit 可能没 realize**
⇒ swizzle 延后到**第一个 runloop**（`dispatch_async` 主队列），
  那时 `main()` 已启动、runtime 完全就绪，但**宿主还没开始建 UI**。

### 2.4 其它真机修的坑

| 问题 | 根因 | 修复 |
|---|---|---|
| T3 设了没反应 | **三重钳制**：硬件上限→T2，低电量→T1，玻璃数量多→T0 | `force_tier`：用户显式定档时跳过所有自动降档 |
| 提前渲染的按钮没玻璃 | 单次上限 40 硬截断 | 渐进式：每轮新增 20，总数 120 |
| 可变形按钮有缝隙 | 按矩形画，按钮实际用 mask path | `OwnShapePath()` 优先复制按钮自己的 mask path |
| 空搜索框被加玻璃 | 黑名单漏 | 改白名单：必须**有可见内容** |
| 圆形按钮被加玻璃 | 没检测圆形 | `LooksCircular()`：w≈h 且圆角≈半宽 ⇒ 跳过 |
| 设置页列表行没玻璃 | `UITableViewCell` 不是 `UIControl`，第一步就被排除 | 候选范围扩成四类（含 cell） |
| 设置行查不到底 | 底色在 `UIBackgroundConfiguration` / `UISystemBackgroundView` | 四层查底，第④层找「盖住自己 40% 的有色子视图」 |
| 滑动后玻璃消失 | cell 复用清掉 layer，关联对象指向孤儿 | `EnsureAttached()` 每轮检查 layer 是否在树上 |
| 恢复慢 | 巡检 3s | 缩到 1.2s + hook `prepareForReuse` 即时补叠 |

## 三、❌ 气泡：我为什么失败了（12 个版本的错误链）

### 3.1 错误链

| 版本 | 我以为是 | 实际是 |
|---|---|---|
| v49 | 气泡是「有圆角+有底色」的视图 | 宿主气泡 **r=0、bg=透明**，视图树里一个都没有 |
| v50 | 改外层 `UserBubbleView` | 它有 padding，染到了外围 |
| v52 | AI 侧认 `ResponseFragmentView` | 那是**内层文字容器** |
| v55 | 气泡在视图树里 | **在 ivar `bubbleView` 里** |
| v57 | 改 `backgroundColor` | 把宿主那层整个换掉，**文字填充色没了** |
| v58 | 加尺寸校验就够了 | 量到的文字包围盒是**内容高度 832**，不是可视高度 |
| v60 | 用「文字包围盒 + padding」 | `RequestFragmentView` 是**可滚动容器**，832 高被夹成整块大方块 |

### 3.2 真机 dump 出的真实结构

```
UserRequestBubbleView  414x228
  UserBubbleView       320x228  r=0.0  bg=#000000/0.00   ← ivar.bubbleView
    UIView             288x208  r=0.0  bg=nil
      RequestFragmentView 288x832        ← ★ 可滚动文字容器，内容比可视高得多
        _UITextContainerView
    DeepSeek_Chat.UserMessageFoldButton 320x36
```

### 3.3 核心失败原因

**我从来没有先把「气泡到底应该多大」这件事弄清楚，就动手了。**

具体地：
1. `bubbleView.bounds` = 320x228，但它内部装的是**可滚动容器**（288x832）
2. 我想量「文字在哪」，量到的是**内容尺寸 832**，不是可视尺寸
3. 夹到容器 bounds 里 ⇒ 变成 228 高的整块
4. 于是出现「蓝色大方块，文字只占左上角」

### 3.4 如果重来，正确顺序应该是

1. **先**写一个纯诊断模式：只针对一条消息，打印
   - `bubbleView` 的 `frame` / `bounds` / `contentOffset` / `clipsToBounds`
   - 每个子视图同样的一套
2. 从数据里确定「气泡的可视区域由谁定义」
3. **再**动手画

代价对比：
- 诊断：一次 dump，5 分钟
- 我实际做的：12 个版本 × (编译+部署+重启+求你拍照) ≈ 2 小时

> 这条正是文档 30 写的铁律：**一次 dump 胜过六次猜测**。
> 我知道它，但我没执行它。

## 四、其它真机收获

### 4.1 只能靠 SSH（MCP 不可用）

设备上的 `ios-mcp` 是全的（`com.witchan.ios-mcp 1.2.8`，dylib 也在
`/var/jb/usr/lib/TweakInject/`），但 8090/8070/8080 全部 `Connection refused`
—— 它注入到 `com.deepseek.chat` 进程，而该进程没监听端口。

⇒ 本轮全程用 SSH + 日志 + 视图树 dump 验证，没有截图。

### 4.2 设备上缺工具

`sysctl` / `netstat` / `xxd` / `strings` / `pgrep` / `awk` 全部没有。
⇒ 需要系统信息时，改用 `hw.ncpu` 之类只能从**进程内**读（`sysctlbyname`）。

### 4.3 ⚠️ `rm -f fdm.log` 会骗你

App 正在写日志时 `rm` 掉文件，进程继续写那个**已删除的 inode**
⇒ `cat` 看不到新内容，但功能其实正常。

**教训**：要清日志就 `killall` 让 App 自己重开，不要 `rm`。

### 4.4 设备的真实硬件参数（和常识不一样）

| 项 | 期望 | 真机实测 |
|---|---|---|
| `hw.ncpu` (A10) | 4 | **2**（2大+2小，同时只跑一组） |
| `hw.physicalcpu` | 4 | **2** |
| `hw.memsize` | 3072MB | **2999MB** |

⇒ 评分阈值全部要留 100~200MB 余量，否则 3GB/4GB 机型都会被低估一档。

## 七、给下次的三句话

> **1. 我违反了「先 dump 再动手」，付出了 12 个版本的代价。**
> 气泡这块，如果第一次就 dump 出「bubbleView 里装的是 288x832 的可滚动容器」，
> 后面 10 个版本全都不用做。**知道铁律 ≠ 执行铁律。**

> **2. 构造函数里能做的事，比你想象的少得多。**
> 只能 swizzle，不能碰 Foundation；只能加方法，不能改父类方法表。
> 真正的业务逻辑必须等首个 runloop 之后 —— 那时已经足够早。

> **3. 「改属性」永远不如「加图层」。**
> 改 `backgroundColor` 会把宿主那层整个换掉（渐变/半透明全丢）；
> 插一个 `zPosition = -1` 的 CALayer，撤掉时宿主瞬间恢复原样。
