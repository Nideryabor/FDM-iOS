### 视图树工具能看到的（这是最有价值的资产）

```
类名  f=(x,y wxh)  b=(wxh)  面积%  bg=#RRGGBB/α  sl=子层数  标签
```

标签自动标注：

| 标签 | 含义 |
|---|---|
| `SCROLL`/`TABLE`/`COLL` | 滚动容器 |
| `BLUR` | 毛玻璃 |
| **`LBG`** | **有 layer 背景**（view 背景透明但 layer 有色 —— 最难查的就是这种）|
| `MASK` | 有 layer.mask |
| `INVISIBLE` | alpha < 0.01 |
| `★FGIMG`/`★DIM`/`★CELLDONE` | 我们加的视图 |

## 三、⭐ 逆向得到的宿主 UI 真相

### 3.1 页面类名对照

```
DeepSeek Chat/Pages/Session/
├─ SessionList/SessionListViewController.swift   → _TtC13DeepSeek_Chat25SessionListViewController
└─ SessionMessage/MessageViewController.swift    → _TtC13DeepSeek_Chat21MessageViewController
```

⚠️ **Swift mangled 类名里的数字是字符串长度**，写错一个 `objc_getClass` 就返回 nil，静默失败：

```
_TtC13DeepSeek_Chat21MessageViewController      ← 21 = "MessageViewController".length
_TtC13DeepSeek_Chat25SessionListViewController  ← 25
_TtC13DeepSeek_Chat21SessionViewController      ← 21（抽屉容器，不是列表！）
```

### 3.2 消息页的「黑」来自三个遮罩（不是气泡容器）

视图树实锤：

```
DeepSeek_Chat.VariableBlurView  f=(0,0 414x214)   ← 顶部毛玻璃，盖 214px
DeepSeek_Chat.DSGradientView    f=(0,20 414x82)   ← 黑色渐变
DeepSeek_Chat.DSGradientView    f=(0,-112 414x214)
```

它们画在 **CALayer 的 gradient / blur** 上，`view.backgroundColor` 是 `α=0.00`
⇒ 清 backgroundColor 永远清不掉 ⇒ **必须 `alpha = 0` 隐藏**。

### 3.3 设置页是「模态卡片」，有三个漏光点

```
UIWindow
 └ UITransitionView
    ├ UIDimmingView  bg=#252528/0.46           ← 遮罩层（被我们清成 0 了）
    └ UIDropShadowView f=(20,30 374x629) b=(414x696)
       │              ↑ frame<bounds ⇒ 带 transform，四角透明
       └ UITableView
          ├ UIImageView ★FGIMG
          └ UITableViewWrapperView f=(16,0 382x696)
                        ↑ 左右各 16px 不在表格内
```

三个漏点：**卡片圆角外** + **表格左右 16px** + **内容区之外**。

### 3.4 ⚠️ `UITableView.backgroundView` 会跟着滚动（重大发现）

```
刚进页面： UITableView bg=#000000/0.00  sl=13
            └ UIImageView f=(0,-56 ...) ★FGIMG   ← y = -56
滚动之后： UITableView bg=#000000/1.00  sl=3     ← 变纯黑
```

**`backgroundView` 是插在 scrollView 内容层里的**，跟着 `contentOffset` 一起滚。
滚得越多图跑得越远 ⇒ 露出 table 自己的黑底 ⇒ 就是「拉上来变透明」。

⇒ **背景图必须放在滚动视图的「祖先层」**，不能塞进滚动视图里。

### 3.5 气泡类名

```
DeepSeek_Chat.UserRequestBubbleView     ← 用户气泡（那个大黑框）
DeepSeek_Chat.UserBubbleView
DeepSeek_Chat.BaseMessageView / BaseMessageCell
DeepSeek_Chat.RequestFragmentView / ResponseFragmentView
DeepSeek_Chat.AgentMessageCell / UserMessageCell
```

### 3.6 列表 cell 结构

```
InsetsGroupedCell（虚线分组卡片）
  ├ UIView  bg=#1C1C1E/1.00   ← 卡片底色
  └ UIListContentView          ← ★ 真实内容（按钮/开关/箭头）
       ├ _UIListContentImageView
       └ UILabel
  └ _UITableViewCellSeparatorView
```

`UIListContentView` 是「内容边界」——**清理必须在这里停下**，否则按钮会消失。

## 五、💥 数据库层抹除：彻底失败的宣告

**从 v8 到 v13 折腾了 6 个版本，最终放弃并删除全部代码（-21KB）。**

### 为什么失败

宿主 `WCDBSwift.framework` 把 sqlite3 **静态编进自己**（不依赖 libsqlite3.dylib），
所以：

| 尝试 | 结果 |
|---|---|
| 指针表 hook（`__got`/`__la_symbol_ptr`） | ❌ 不是导入符号，没有槽位 |
| 内联 hook `sqlite3_bind_text` | ⚠️ 能挂上，但**调用计数永远是 0** |
| 内联 hook `sqlite3_bind_text16` | 💥 它是 `bind_text + 8`，**不是函数开头**，含 `adrp`（PC 相对）⇒ 搬到跳板必然 SIGSEGV |
| 内联 hook `sqlite3_bind_blob` | 💥 第 0 条是 `tbnz`，目标 `+0x1c` 超出 8 字节覆盖窗口 |

### 更根本的原因

**调用计数永远是 `text=0 blob=0 text16=0`** ⇒ 消息根本不是本地写入的，是**服务端同步下来的**。
这条路从方向就错了。

### 顺带修掉的 3 个通用 bug（这些是真实收获）

1. **`InsnIsPCRelative` 位运算 bug**：`TBZ/TBNZ/CBZ/CBNZ` 的 opcode 在**高 8 位**，
   旧代码用 `insn >> 26`（高 6 位）比较 ⇒ 永远匹配不上 ⇒ 漏判
2. **跳板未对齐**：`*(uint64_t *)(tramp + trampLen + 8)` 当 `trampLen=4` 时地址是 `+12`，
   **不是 8 的倍数** ⇒ ARM64 未对齐 64 位写 ⇒ **SIGBUS**
3. **符号表偏移基点错误**：`symoff`/`stroff` 是**文件偏移**，
   必须走 `__LINKEDIT` 换算，不能直接加 mach header

## 六、💥 其它踩过的坑（按代价排序）

| # | 坑 | 症状 | 教训 |
|---|---|---|---|
| 1 | `class_getInstanceMethod` 沿继承链查找 | 改到了**全局** `UIViewController.viewDidLoad` ⇒ 所有页面崩 | 先判断「自己有没有实现」，没有就 `class_addMethod` |
| 2 | 子类 hook 导致原 IMP 指向自己 | 无限递归爆栈 | hook 前检查 old 是不是自己的 wrapper |
| 3 | `OBJC_ASSOCIATION_ASSIGN` | 野指针（不是 nil）⇒ `if (!host)` 拦不住 | 不存 VC 指针，用时现找 topVC |
| 4 | `NSNumber*` 隐式转 `BOOL` | 配置写 false 却永远返回 YES | `BOOL` 函数别返回 `id` |
| 5 | `MAX_HOOKS = 32` 太小 | 表满后静默失败，有 hook 没记账 ⇒ 网络全废 | 256，且 AddHook 返回 BOOL |
| 6 | signal handler 里用 Foundation | 崩溃时死锁，**日志全丢** | 只用 `write(2)` + static buffer |
| 7 | 往 `UITransitionView` 插背景图 | 退出模态要等图消失 | 转场容器不能碰 |
| 8 | `other_enabled` 贴到系统 window | App 变「单图浏览器」 | `windowLevel != Normal` 一律跳过 |
| 9 | 中文串搜不到 | dylib 里中文是 **UTF-16** | 用 `utf-16-le` 编码搜 |
| 10 | **「假崩溃」三兄弟** | 见下 | —— |

### ⚠️ 「假崩溃」鉴别法（最省时间的收获）

三个现象一模一样（`uiopen` 成功、进程不出现、日志空白），原因完全不同：

| 现象 | 真因 | 判据 |
|---|---|---|
| 起不来 + 日志空白 | **锁屏** | 日志连「启动」都没有 |
| 起不来 + 日志空白 | **内存 < 150MB** | `vm_stat \| grep "Pages free"` |
| 起不来 + 有 `.ips` | 代码 bug | 看 faultingThread 帧 |

> **`tail -3 fdm.log` 有「==================== 启动 ====================」= 模块跑了；
> 完全没有 = App 压根没启动，先解锁/腾内存。**

这条让尼尼少浪费了 5 轮以上。

## 九、💰 方法论

### 遇到「UI 不生效」怎么办

```
① 别猜！先 dump 视图树（FDMUITree）
② 在 dump 里搜目标区域对应的 frame 范围
   例：设置页底部 → 找 f=(0,600+ ...) 的节点
③ 看这些节点的 bg= / LBG / sl= 字段
   • bg=#000000/1.00     → view 背景不透明，清 backgroundColor
   • bg=- 但 LBG         → **layer 背景**，要清 layer.backgroundColor
   • bg=#000000/0.00 但有视觉  → 是 gradient/blur，要 alpha=0
④ 改完再 dump 对比，确认那一行变了
```

### 遇到「改了没效果」怎么办

```
① 加日志确认代码跑了没有
② 跑了但没效果 → 检查「谁在上面盖住了」（视图树从下往上找）
③ 没跑 → 检查匹配条件（类名长度！中文 UTF-16！）
④ 跑了、也没被盖住、但视觉没变
   → 可能是系统在下次布局时覆盖回来了 ⇒ 需要 hook layoutSubviews
```
