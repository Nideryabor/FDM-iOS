## 二、⭐ 为什么 iOS 比安卓简单得多

### 安卓的痛点（GmSender 382 行，一半在处理它）

```
gh2.h0(gh2, 文本, [], [], "", m1a, ns, false, false, false, false)
                                   ↑    ↑
                               目标会话  消息存储
```

宿主进程里**同时活着多个 `gh2` 实例**（每个打开过的会话一个），
拿错了就：
- 发到别的对话（真机踩过：点建议，消息跑到了另一个会话）
- 或直接开一个新会话（尼尼连开 5 个空会话的教训）

他们的解法：hook `gh2.W()`，记「被调得最频繁的那个」+ 15 秒 TTL。

### iOS 的做法：**根本不碰会话 id**

```
往宿主自己的输入框塞文字 → 点它自己的发送按钮
        ↓
宿主自己做完整流程：UI 立即出现、SSE 流式渲染、落库、更新会话列表
```

**天然就是「当前会话」**，不存在选错的可能。

> **方法论**：能在别人已有的流程里"搭车"，就不要自己重建流程。
> 安卓重建了发送链路 ⇒ 必须自己解决"发到哪"；
> iOS 借用了 UI 触发 ⇒ 这个问题从根上消失了。

### 三个坑

| # | 坑 | 现象 |
|---|---|---|
| 1 | **BannerView 里有个 0x0 的 UITextView** | 按 "TextView" 搜会先搜到它，塞字进去毫无反应 |
| 2 | **空输入时 SendButton 容器宽度 = 0**（`f=(88,6 0x24)`） | 立刻找按钮会拿到一个点不动的；必须先塞字再等一帧 |
| 3 | **`presentedViewController` 链找不到聊天页** | 聊天页挂在很深的 VC 树里（Root → 抽屉 → 导航 → MessageVC），只走 presented 会漏 |

## 四、实现要点

### 4.1 精准找控件

```objc
/* 输入框：先定位 TextInputView，再往下找 UITextView —— 避开 Banner 里那个 0x0 */
UIView *wrap = BTFindByName(area, "TextInputView", 0, nil);
UITextView *tv = BTFindByName(wrap, "TextView", 0, [UITextView class]);
/* 尺寸校验：宽 < 100 且高 < 20 的当装饰品跳过 */

/* 发送键：先定位 SendButton 容器，再在它里面找第一个 UIButton */
UIView *cont = BTFindByName(area, "SendButton", 0, nil);
UIButton *btn = BTFindByName(cont, "Button", 0, [UIButton class]);
```

### 4.2 塞文字必须手动发通知

`setText:` **不会**触发 `UITextViewTextDidChangeNotification` ——
而宿主是靠这个通知把 SendButton 撑开的。

```objc
tv.text = text;
[[NSNotificationCenter defaultCenter]
    postNotificationName:UITextViewTextDidChangeNotification object:tv];
if (tv.delegate && [tv.delegate respondsToSelector:@selector(textViewDidChange:)])
    [tv.delegate textViewDidChange:tv];
```

### 4.3 等一帧再点按钮

```objc
dispatch_after(dispatch_time(DISPATCH_TIME_NOW, (int64_t)(0.25 * NSEC_PER_SEC)),
               dispatch_get_main_queue(), ^{
    UIButton *btn = BTFindSendButtonExact(area);
    [btn sendActionsForControlEvents:UIControlEventTouchUpInside];
});
```

### 4.4 用 `sendActionsForControlEvents:` 而不是直接调 target-action

这样宿主自己的全部校验都会跑一遍（比如「正在生成时禁止发送」），
不会绕过业务逻辑造成状态错乱。

### 4.5 找 VC 不能用 presentedViewController 链

```objc
/* ❌ 只走 presentedViewController ⇒ 聊天页永远找不到 */
/* ✅ 递归 children / nav / tab / presented，找不到就退回 window */
```

## 五、两条路（都已实现）

| 路 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A · 推荐** | 塞输入框 + 点发送键 | 宿主走完整流程；UI 立即出现；自动落库 | 依赖 UI 结构（本次已探明） |
| **B · 兜底** | 抓真实 completion 请求当模板，改 prompt 重放 | 一定成功，不依赖 UI | UI 不会自动刷新，要等宿主自己拉历史 |

```objc
BOOL FDMComposerSend(NSString *text) {
    if (FDMComposerSendViaUI(text)) return YES;     /* 先走 A */
    return FDMComposerSendViaReplay(text);          /* 再退 B */
}
```

### 路 B 的关键：请求模板

抓到的真实请求体（`fdm-req-raw.json`）：

```json
{
  "prompt": "你好",
  "chat_session_id": "e33b27fb-****-****-****-************",
  "model_type": "default",
  "thinking_enabled": true,
  "search_enabled": true,
  "parent_message_id": null,
  "preempt": false,
  "action": null,
  "audio_id": null,
  "ref_file_ids": []
}
```

重放时只改 `prompt` 和 `parent_message_id`，其余原样保留，
并且要用 `FDMProbeSetReplay(YES)` 标记，**避免被自己的注入 hook 二次处理**。
