## 〇、现象

`fdm6.log` 里 **每 3~5 秒一条启动记录**，全部停在同一个位置之后：

```
16:22:40  pid=5179  网络挂钩完成：改了 19 处 → 崩
16:22:45  pid=5180  网络挂钩完成：改了 19 处 → 崩
16:22:48  pid=5182  → 崩
16:22:51  pid=5183  → 崩
```

⇒ **崩溃循环**，且 `fdm6-req-body.json` / `fdm6-hits.txt` / `fdm6-images.txt` **全都没生成**
（说明连 3 秒后的定时任务都没跑到）。

---

## 一、根因（两个错误，第二个是致命的）

### 错误 ①：hook 了无关的系统框架类

v0.6 用"类名含 URLSession 就挂"的粗暴策略，结果挂了 **19 处**，其中这些**跟 DeepSeek 毫无关系**：

```
AMSURLSession                    ← App Store / Media Services
ACSURLSession                    ← 系统认证（ACSystem）
WebCoreNSURLSession              ← ★ WebKit！
C2NetworkingDelegateURLSession   ← iCloud
__NSCFURLSessionTaskGroup        ← 内部辅助类
```

它们**在 App 启动期就会被用到**（WebView、iCloud、商店校验），一 hook 就炸。

### 错误 ②（致命）：所有类共用同一个「原始 IMP」

```c
/* v0.6 的代码 */
if (*olds[s] == NULL) *olds[s] = cur;     // ← 只记第一个类的原函数
method_setImplementation(m, news[s]);
```

于是 **19 个方法全部指向同一个 wrapper**，而 wrapper 里调的却是
**第一个被 hook 的那个类的原函数**：

```
WebCoreNSURLSession 的方法被调用
   → 进入我们的 wrapper
   → 调用 o_dataTask（其实是 AMSURLSession 的原函数）
   → self 是个 WebCore 实例，类型完全不匹配
   → 💥
```

## 二、v0.7 的修法

| # | 修法 |
|---|---|
| ① | **白名单**：只碰名字精确等于 `NSURLSession`、或以 `__NSCF`+含`URLSession`、或以 `__NSURL` 开头的类 |
| ② | **每 (类, 方法) 各记一份原始 IMP** —— `HookEntry gHooks[32]` 表 |
| ③ | **查表沿继承链走**：`FindOrig(object_getClass(self), _cmd)` 逐级向上找，找到最匹配的那个 |
| ④ | **查不到就安全放弃**：返回 nil 并记日志，**绝不乱调** |
| ⑤ | 新增诊断：启动时**列出进程里所有 URLSession 家族类**（★ 标记会被 hook 的） |
| ⑥ | 新增总开关 `fdm-net.json` → `{"enabled": false}` 可一键关掉网络 Hook |

### 核心修复代码

```c
typedef struct { Class cls; SEL sel; IMP orig; } HookEntry;
static HookEntry gHooks[MAX_HOOKS];
static int gHookCount = 0;

static IMP FindOrig(Class cls, SEL sel) {
    for (Class c = cls; c != Nil; c = class_getSuperclass(c))
        for (int i = 0; i < gHookCount; i++)
            if (gHooks[i].cls == c && sel_isEqual(gHooks[i].sel, sel))
                return gHooks[i].orig;
    return NULL;                       /* 找不到 → 调用方安全放弃 */
}

/* wrapper 里 */
IMP o = FindOrig(object_getClass(self), _cmd);
if (!o) { Q(@"!! 找不到原函数"); return nil; }
return ((...))o(self, _cmd, r);
```

## 三、教训（值得记进项目铁律）

| # | 铁律 |
|---|---|
| 1 | **别用"类名包含 xx"做大批量 hook** —— 会误伤系统框架，而那些类在启动期就活跃 |
| 2 | **每个 (类, 方法) 必须各记一份原始 IMP** —— 共用一个 = 用错误的自类型调函数 = 必崩 |
| 3 | **hook 之前先列出候选类**，肉眼确认哪些是自己要的 |
| 4 | **wrapper 里查不到原函数要安全退出**，绝不能拿别的函数的指针硬调 |
| 5 | 每个高危 hook 都要有**独立开关**，出事能一键关 |

> 与 v0.2/v0.3 那次崩溃对比：
> - **v0.2/v0.3**：Hook **太重**（性能/重入/IO）→ 表现为"跑一会儿崩"
> - **v0.6**：Hook **错对象**（调错 IMP）→ 表现为"启动即崩循环"
> 两种是不同的病，都得防。

## 四、主人现在这么做

### 1) 先确认能跑（关键一步）

TrollFools → DeepSeek → **移除旧注入（v0.6 一定要去掉）** → 注入 **`FDMProbe-v0.7.dylib`**

启动 → **看是否还崩**：
- **不崩了** → 继续第 2 步
- **还崩** → 说明还有别的雷。**先看 `fdm7.log` 停在哪一步**
  （若仍疑似网络 Hook，放个 `fdm-net.json` 写 `{"enabled": false}` → 若立刻就好，那就锁定是网络 Hook）

### 2) 发一条消息，抓请求体

发消息 → 取 `Documents/fdm7-req-body.json` → **给尼尼**

### 3) 若还崩，日志会告诉我们在哪

`fdm7.log` 现在有分阶段标记：
```
FDM v0.7 已加载
配置：...
MMKV 挂钩：...
URLSession 家族类：...        ← ★ 新增，看有哪些
   挂 NSURLSession -dataTaskWithRequest:  ← 只会挂这几个
网络挂钩完成：N 处
3s 阶段完成
45s：...
```
