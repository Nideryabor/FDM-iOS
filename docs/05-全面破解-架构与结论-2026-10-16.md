```

| 假设 | 结论 |
|---|---|
| A. 探针太重（Hook/IO） | ✅ **成立** —— 零 Hook 就稳 |
| B. 反作弊检测注入 | ❌ 排除（注入存在，但没被干） |

⇒ **可以安全下结论：Hook 本身是崩溃源，反作弊目前没在管注入。**
（但不代表以后不管 —— 登录/风控场景仍需警惕。）

### v0.2/v0.3 崩溃的三个真凶（复盘）

| # | 错误 | 修法 |
|---|---|---|
| 1 | `MMKVID(self)` → 调宿主方法 `[self mmapID]`，在 MMKV 锁内又碰 MMKV | 不调宿主方法 |
| 2 | `mmkvWithID:` 被调 **11961 次**（登录后按用户 UUID 反复取），每次都 NSLog+写盘 | 去重 + 后台异步刷盘 |
| 3 | Hook 内同步做文件 IO | 内存缓冲 + 定时刷 |

⇒ **规矩**：Hook 内只做 O(1) 内存操作；不调宿主方法；日志走缓冲。

## 二、⚠️ 最大隐患：ElleKit 注入了 13 个无关 tweak

`fdm2-images.txt` 实测（DeepSeek 进程内）：

```
libellekit.dylib                              ← 注入框架本体
TweakInject/noJailbreak.dylib                 ← ★ 越狱检测/绕过
TweakInject/AFHook.dylib                      ← AppList hook
TweakInject/Choicy.dylib                      ← ★ 按 App 控制注入（神器）
TweakInject/Spectrum.dylib                    ← tweak 管理器
TweakInject/Snowboard.dylib + aaaSnowBoardUISB + AAAASnowBoardFontsSB + SnowBoardStatusBarSB
TweakInject/AFont.dylib
TweakInject/3DAppVersionSpoofer.dylib         ← 版本伪装
TweakInject/Cask3.dylib
TweakInject/LimneosCrack.dylib
TweakInject/locsuperunit.dylib
Frameworks/FDMProbe-v0.4.dylib                ← 我们自己的
```

**风险**：
- 这么多 tweak 注入 → **相互冲突**是崩溃的常见原因（v0.2/v0.3 的崩，可能也有它们掺一脚）
- `libellekit.dylib` 在进程里可见 → 反作弊一抓一个准
- 我们走 TrollFools，**根本不需要 ElleKit 注入 DeepSeek**

### ⭐ 行动建议（零成本、收益大）

**用 `Choicy`**（已经装了！）——把 DeepSeek 的 ElleKit 注入**关掉**：
1. 打开 Choicy → 找到 DeepSeek
2. 关闭该 App 的 tweak 注入（或只保留必要的）
3. 重启 DeepSeek

这样：
- 进程内不再有 `libellekit` 和那 13 个 dylib → **反作弊面大幅缩小**
- **冲突源消失** → 我们的 Hook 类探针（v0.3 路线）有机会稳定运行

```
MMKV 实例 : mmkv.default
键        : app.ab.serverValues

## 五、⭐ MMKV 文件格式（已破解）

```
偏移 0   : uint32 LE  actualSize
偏移 4   : 4 字节（crc/flag）
偏移 8   : 条目流（append-only 日志）

每条目：
  varint32  keyLength
  bytes     key (UTF-8)
  varint32  valueLength
  bytes     value
             └─ 内部：varint32 innerLen + payload（payload 通常就是 JSON 文本）
```

**验证**：
```
mmkv.default : actualSize=176460, 解析出 25 条（含重复，日志式）
              最终有效 10 键
<UUID>       : actualSize=37138,  解析出 56 条 → 最终有效 14 键
```

⇒ **重大意义**：以后**拿到 MMKV 文件就能离线解析**，不必跑探针、不必注入。
（可以用 Filza 直接把 `Documents/mmkv/*` 拖出来分析。）

## 六、⚠️ 安全提醒

`mmkv.default` 里的 **`currentUser`** 含：
```json
{"settingsToken":"eyJhbGciOiJkaXIiLCJlbmMiOiJBMjU2R0NNIn0..<...>", ...}
```
这是 **`x-settings-token`**（服务端下发鉴权 token，JWE 格式）。

- 主人把 Documents 整个打包给尼尼时，**它也跟着来了**
- 尼尼已在输出里**刻意省略**，未落盘到 analysis
- ⚠️ **建议**：这份 token 如果被泄露，别人可以拿它以你的身份拉设置。
  **如果主人在别处分享过这批文件，建议到 App 里退出登录再登一次（会换新 token）。**

## 七、下一步方案（路线已清晰）

### 7.1 先做的事（零风险、高收益）

1. **用 Choicy 关掉 DeepSeek 的 ElleKit 注入** → 去掉 13 个 tweak 的干扰
2. 然后**重跑 v0.3（带 Hook 版）** —— 如果不再崩，说明是 tweak 冲突；如果还崩，说明是 Hook 写法

### 7.2 业务实现路线（iOS 版）

**目标：让宿主读到我们想给的值。**

| 方案 | 做法 | 难度 |
|---|---|---|
| **A. 写 MMKV**（对应安卓思路） | Hook `AppMMKVEngine`/直接写 `mmkv.default` 与用户实例 | ⭐ 需先定位"用户实例 ID 从哪来" |
| **B. 改 blob** | 改 `app.ab.serverValues` 里对应 key 的 value | ⭐⭐ 简单粗暴，但宿主可能缓存 |
| **C. Hook 读取层** | Hook `RemoteSettingsManager.localStorageGetter` / `LazySettingReader` | ⭐⭐⭐ 最干净，需运行时拿实例 |

> 尼尼建议 **先用 A**（最接近安卓已验证的思路），失败再上 C。

### 7.3 系统提示词注入（对照安卓专题）

iOS 侧线索已找到：
- `modelConfig_1` 里有 **`prompt_feature`**（含 `{"id":9,"scene":"image","content":"这是什么"}`）
- `InputAreaView+PromptInputView` / `PromptSuggestionView`

⇒ 下一步用 v0.3 的 Hook 能力，抓**真正的请求组装点**。
